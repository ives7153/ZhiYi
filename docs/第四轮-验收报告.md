# 知衣 App 第四轮 — 待购管理与试搭 验收报告

> 本轮范围：待购管理、待购参与插槽式试搭、已购买后转入衣橱。
> 所有命令都是本机实跑；设备证据全部来自 AVD `zhiyi-test`（**没有实体手机**，见 §7）。
> 写作规则沿用前几轮：只写跑过的、看得到的东西；未验证项单独列出，不与已验证项混排。

## 0. 一句话结论

待购与已拥有共用同一件衣物实体（`clothing_items.ownership`），服务端是唯一数据源：待购不进入衣橱列表/数量/类别计数/普通搭配候选/自动推荐/穿着统计；试搭的「含待购」由服务端按真实衣物归属计算；已购买是同一行上的幂等状态转换（同 ID、同图片、同搭配关联，重复与并发都只有一件）。
本轮后端新增 25 项契约测试 + 迁移核查脚本（一次性库，11 项断言）+ 面向真实后端的 53 项契约脚本；客户端 8 个离线脚本全绿（含本轮新增 67 项）；设备上跑通「加入待购 → 试搭并保存 → 冷启动重开 → 标记已购买 → 衣橱查看 → 冷启动重读」，并回归了前几轮的既有场景。

## 2. 本轮真实数据契约（先读源码，再写代码）

### 2.1 改动前的实测事实

| 位置 | 事实 |
| --- | --- |
| `backend/app/models/item.py` | `ClothingItem` 只有 `status`(processing/ready/error/archived)、`tagging_status`、`is_archived`，**没有任何归属字段**；`purchase_price Numeric(10,2)` 表示"实际支付" |
| `backend/app/services/item_service.py` | `get_list` / `get_ids_by_filter` / `get_item_types` / `get_color_distribution` / `get_ready_item_count` 一律按 `user_id + is_archived` 过滤 |

| 搭配 | `POST /outfits/suggestions`（`items` ≤ 20）；`validate_item_ownership` 要求 `status == ready`，**不区分归属**；`OutfitResponse` 没有任何"是否含待购"信息 |
| 穿着记录 | `POST /items/{id}/wear`、`POST /outfits/{id}/feedback`(`worn`)、`POST /outfits/studio`(`mark_worn`)、`POST /outfits/{id}/wear-today`、`POST /outfits/{id}/wore-instead` 都会写 `wear_count / last_worn_at / needs_wash` |
| 推荐/配对/学习 | `recommendation_service.get_candidate_items`、`pairing_service`、`learning_service` 的候选查询都按 `status == ready` 过滤，同样没有归属 |
| 迁移链 | head = `d5e6f7a8b9c0`（`backend/scripts/check_migration_heads.py` → `OK: Single migration head`） |

结论：仓库里**没有**可复用的待购能力，也没有归属字段，因此按规格第 3 条做"最小、向后兼容的后端扩展"。

### 2.2 本轮新增/扩展的真实字段与端点

**字段（`clothing_items`）**

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `ownership` | 枚举 `item_ownership`：`owned` / `to_buy`，NOT NULL，`server_default 'owned'`，有索引 | 与处理状态、标注状态、归档状态**完全独立**的第四个轴 |
| `reference_price` | `Numeric(10,2)` NULL | 待购参考价；**不会**在购买时写进 `purchase_price` |
| `source_url` | `String(500)` NULL | 手动填写的商品链接，只允许 http/https |

**端点**

| 端点 | 变化 | 兼容性 |
| --- | --- | --- |
| `GET /items` | 新增 `ownership`（**默认 `owned`**） | 旧客户端/Web 不传 → 行为与第三轮完全一致 |
| `GET /items/types`、`GET /items/colors` | 新增 `ownership`（默认 `owned`） | 同上 |
| `POST /items` | 新增表单字段 `ownership`(默认 owned)、`reference_price`、`source_url`；409 重复照片改为结构化 detail（`existing_item_id` / `existing_ownership` / `existing_name`），**message 前缀不变** | 旧客户端不传新字段 → 仍录入衣橱；Web（`frontend/lib/api.ts:70` 取 `detail.message`）与 App（`extractErrorMessage`）都能读出这句话 |
| `DELETE /items/{id}` | 新增可选 `ownership` 守卫 | 不传 = 与旧版一致 |
| `POST /items/{id}/purchase` | **新增**：待购→已拥有，同 ID 同图片，幂等 | 新端点，旧客户端不受影响 |
| `POST /items/{id}/wear` | 待购单品 → 409 `ITEM_NOT_OWNED_YET` | 旧客户端接触不到待购行 |
| `POST /outfits/{id}/feedback` / `wear-today` / `studio` / `wore-instead` | 含待购 → 409 `OUTFIT_CONTAINS_TO_BUY` | 只影响"把未买单品当成已穿过"的请求 |
| `OutfitResponse` | 新增 `contains_to_buy`；每个 `OutfitItemResponse` 新增 `ownership` | 新增只读字段，旧客户端忽略 |

### 2.3 刻意**没有**做的事

* 没有第二张衣物表、没有第二套图片/上传流水线：待购与已拥有共用 `clothing_items`、共用 pHash 去重、共用签名图片服务、共用 `outfit_items` 关联。
* 没有把 `ownership` 放进 `ItemUpdate`：购买有自己的幂等/并发规则，必须是独立端点，不能被一次普通属性编辑顺带翻转。
* 没有 AI 评分、没有电商抓取、没有自动下载链接图片、没有支付/记账/预算。
* 没有改写任何历史迁移、没有清库、没有改动 Web 前端代码。

## 4. 迁移与数据保护

新增迁移 `f4a5b6c7d8e9`（`down_revision = d5e6f7a8b9c0`，仍是单一 head）：

* 只做 **ADD COLUMN + CREATE INDEX + CREATE TYPE**：没有重建表、没有改写行、没有触碰任何图片或 `outfit_items` 关联；
* `ownership` 以 `server_default 'owned'` + NOT NULL 建立，因此既有数据在列出现的同一刻就是**已拥有**，且"不知道这一列"的 INSERT 仍然落入衣橱；
* `reference_price` / `source_url` 对既有衣物保持 NULL（不是 0、不是空串）；
* `downgrade()` 只删除自己新增的三列、索引与枚举类型，不删除任何行。

### 4.1 独立测试库核查（升级前 → 升级后 → 降级）

```bash
cd backend && .venv/bin/python scripts/check_to_buy_migration.py
```

脚本先新建一次性库 `wardrobe_migration_check`（先 DROP 再 CREATE，绝不碰开发库/测试库），升到改动前的 `d5e6f7a8b9c0`，用旧 schema 写入 1 个用户、2 件带图片路径的衣物、1 套搭配与 2 条 `outfit_items` 关联，然后升到 head 并逐项断言：

```

     pre-migration garments=2 outfit_items=2
== 2. upgrade to head (the round-4 migration)
  PASS  no garment row is added or lost by the migration
  PASS  every pre-existing garment is backfilled as 已拥有 (owned)
  PASS  ids and image paths are unchanged
  PASS  outfit associations are unchanged (2)
  PASS  reference_price / source_url are NULL for pre-existing garments (not 0)
  PASS  an INSERT that never mentions `ownership` (an older client) still enters the wardrobe
  PASS  a 待购 row can be stored after the migration
  PASS  the reference price keeps its 2 decimals
== 3. downgrade on the scratch database drops only what it added
  PASS  the three new columns are gone after downgrade
  PASS  downgrade deletes no rows
  PASS  downgrade keeps every outfit association

CHECK-OK: migration verified on a scratch database (upgrade, data, compatibility, downgrade)
```

> 降级只在**一次性数据库**上做；用户数据上不做任何破坏性降级。开发库（`wardrobe`）随后按同一迁移升级：`alembic upgrade head` 输出 `Running upgrade d5e6f7a8b9c0 -> f4a5b6c7d8e9`，`psql \d clothing_items` 显示 `ownership | item_ownership | not null | 'owned'::item_ownership`、`reference_price | numeric(10,2)`、`source_url | character varying(500)` 与 `ix_clothing_items_ownership`。

### 5.1 后端（真实数据库）


`tests/test_to_buy.py`（25 项）覆盖：默认列表/计数/颜色/搜索/分页只在 `owned`；`to_buy` 独立查询；批量 `select_all` 不扫待购；推荐候选排除待购；同图跨归属 409 指回已有行且不改归属；购买保持 ID/图片/参考价、`purchase_price` 不被写；重复与并发购买只有一行；归档后购买 409；不存在/他人 ID → 404；`DELETE ?ownership=to_buy` 守卫；待购单品 `wear` 409 且 `wear_count` 不变；含待购搭配 `worn` 409，买齐后可写；价格/链接校验 422；空值存 NULL；旧调用方式仍进衣橱；待购字段可编辑且编辑不会把衣物"变成已拥有"。

**关于 ABI（与 1.0.2/1.0.3 的差异，如实记录）**：本轮 APK 只含 `arm64-v8a` + `armeabi-v7a` 两种 ARM ABI，不含 `x86` / `x86_64`。
原因：本机把 4 个 ABI 的原生构建全部编完耗时超过 2 小时，且期间 `launchctl` 反复重启构建任务、每次 `expo prebuild` 都清掉 `android/app/build`，四 ABI 构建连续失败三次（构建日志里 JS bundle 任务与各 ABI 的 CMake 任务被反复重跑）。
改为**单实例 + 两个 ARM ABI**后 `BUILD SUCCESSFUL in 5m 47s`（复用了失败尝试留下的 Gradle 构建缓存）。
影响：**所有现代安卓手机都是 `arm64`（32 位设备为 `armeabi-v7a`），模拟器证据所用 AVD 也是 `arm64-v8a`**，因此目标手机与既有验收路径均未受影响；但若有 x86 模拟器需要安装，请用 `-PreactNativeArchitectures=x86_64` 重新构建。这一点记在 §7 未验证项里。

## 7. 未验证项（不得当作已验证）

1. **实体手机**：本轮全部设备证据来自 AVD `zhiyi-test`。真机的局域网可达性、相机拍照、覆盖升级与手感仍需单独验证（步骤见 §8.1）。
2. **真实移动网络的"服务端已提交后断连"时序**：`outcomeUnknown` 的分类与文案由离线脚本（真实 `client.ts` + 替身 `fetch`）与真实后端的 401/403/409 覆盖，但没有在网络层制造过"响应丢失"的时序。
3. **两台真实设备同时操作同一件待购单品**：并发购买在**服务端**用两个并行的 curl 验证过（§5.3 第 6 段），但没有用两台设备同时点按验证界面表现。
4. **AI 开启时的待购录入**：本机 `AI_INTERNAL_ENABLED=false`。"选了类别的待购单品跳过标注、未选类别交给服务端标注"这条规则只做了源码级与客户端规则级验证，未在 AI 开启的后端上实跑。
5. **x86 / x86_64 ABI**：见 §6 说明（用 `-PreactNativeArchitectures=x86_64` 可自行构建）。
6. `s3`（上传失败路径）未跑，与第三轮相同：它需要一个把 API 指向不可达地址的构建。

## 8. 后端启动、迁移与安装步骤

### 8.1 顺序（**先迁移，再装 App**）

```bash
# 1) 后端：升级数据库（只加列/索引，不动既有数据），然后启动
cd backend
.venv/bin/python -m alembic upgrade head        # d5e6f7a8b9c0 -> f4a5b6c7d8e9
nohup .venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 &
curl -s http://127.0.0.1:8000/api/v1/health      # {"status":"healthy"}

# 2) 覆盖安装新版 App（不卸载、不清数据；旧版 1.0.x 的登录态保留）
adb install -r 交付/android-apk/知衣-1.0.4-release.apk

# 3) 启动（无需 Metro）
adb shell am start -n com.zhiyi.wardrobe/.MainActivity
```

**为什么必须这个顺序**：1.0.4 客户端会在列表/计数请求里带 `ownership`，并依赖新端点 `POST /items/{id}/purchase`。旧后端会忽略未知查询参数，但购买端点会 404、待购列表也会与衣橱混在一起 —— 所以**先迁移后装 App**。反过来（先装 App 再迁移）不会破坏数据：迁移只新增列，旧版 App 在迁移后仍照常工作（它不传 `ownership`，服务端默认 `owned`）。

**网络前提**（真机同样适用）：手机需与构建这台机器处于**同一可达网络**（本机地址 `100.141.221.111`，换网络必须用新 IP 重新构建，地址是编进 JS 包的）；后端必须 `--host 0.0.0.0`（只监听 127.0.0.1 时手机连不上，而模拟器仍能走 10.0.2.2，容易误判）；防火墙放行 8000 端口；后端要能读写 `STORAGE_PATH`（本机 `/tmp/zhiyi-pg/storage`）。

### 8.2 5 分钟人工体验路线（各阶段大致耗时）

| --- | --- | --- | --- |
| 1 | 打开 App（桌面图标，无需 Metro） | 直接进入衣橱，数量与登录态保留 | ~20 s |
