## 有证据的必须修复问题

### 1. 旧分析与标注统计把待购计入衣橱

**位置：** `backend/app/api/analytics.py:90-108,155-238` 的衣橱总量、ready、颜色/类别分布、未穿/最常穿查询均仅限 `user_id`（部分限 ready），无 `ownership=owned`；`backend/app/api/items.py:1063-1073,1192-1246` 的 `_tagging_scope` 也无归属条件；调用方 `frontend/lib/hooks/use-analytics.ts:71-72`、`frontend/app/dashboard/analytics/page.tsx:225-239,381-400`，Web `frontend/lib/hooks/use-items.ts:66-67`。这两个旧接口不同于已过滤的 `/items` 和 `/items/types`。

**实测复现：** 在**测试库**创建仅 1 件 `ready/to_buy`、无 owned 的自建账号，同 token 请求 `GET /api/v1/items` 为 `total=0`，`GET /api/v1/items/tagging-progress` 却为 `total=1`，`GET /api/v1/analytics` 的 `wardrobe.total_items=1`、`items_by_status.ready=1`、`never_worn` 含该待购 ID。测试账号及记录已清理。

**影响：** Web 衣橱统计、未穿列表及标注进度和 App 衣橱实际数量自相矛盾；待购混入“衣橱数量/穿着统计”展示。应在这两个旧衣橱语义端点按 `owned` 服务端过滤，并用仅待购账号加回归断言（不应把试搭本身隐去）。

### 2. 购买与陈旧待购页删除交错时仍可误删已拥有衣物

**位置：** `backend/app/api/items.py:1310-1364` 中 `DELETE /items/{id}?ownership=to_buy` 先 `get_by_id` 读取并比较归属，随后先删图片、再 `item_service.delete(item)`；未对检查与删除做原子条件约束或行锁。购买路径 `backend/app/api/items.py:1406-1465` 并发更新同一行。

**受控请求复现：** 在**测试库**自建 `to_buy` 衣物，将测试进程中 `ItemService.get_by_id` 对删除任务的返回暂缓（不修改产品源码），顺序为：删除请求已读取待购行 → 另一个请求购买返回 `200 owned` → 恢复删除请求 → 删除返回 `204` → 同 ID `GET` 返回 `404`。自建账号与记录已清理。顺序购买后再删除的现有测试确实返回 409，但不覆盖该交错。

**影响：** 两设备或超时重试时，用户刚买入的衣橱单品与图片/搭配关联可能被另一陈旧页物理删除；本轮承诺的归属守卫失效。需要在数据库事务中原子验证“仍为 to_buy 才删除”（并使图片删除服从最终数据库结果），增加受控并发回归；旧客户端不带守卫的删除语义另行保持。

### 3. 待购新增字段校验失败后遗留孤儿图片

**位置：** `backend/app/api/items.py:242-278` 先 `ImageService.process_and_store` 写文件，再构建/校验含 `reference_price`、`source_url` 的 `ItemCreate`；`backend/app/services/image_service.py:119-180` 确实写原图/中图/缩略图，校验错误分支没有清理。该顺序在第四轮引入新校验字段后可由正常用户输入触发。

**实测复现：** 只在测试库创建自建账号，`STORAGE_PATH` 指向本会话 scratch 目录，上传有效 JPEG，`ownership=to_buy&reference_price=1.234`：响应 **422**、衣物行 **0**、该账号目录留下 **3 个 jpg**。随即清理该账号和图片。`source_url=javascript:...` 经过相同先存后校验路径。

**影响：** 用户纠正价格/链接重复提交时会不断留下不可由衣物记录清理的文件，耗尽存储并使上传结果与图片存储不一致。应先校验表单字段再写图片，或在验证/写库异常时清理刚写入的图片，并补 422 后无孤儿文件的定向测试。
