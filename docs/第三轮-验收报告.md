## 0. 一句话结论

第三轮可以交付：搭配占位页已变成按**上衣/下装/外套/鞋子/配饰**五个席位选真实衣物的功能，
可以命名保存、在「已保存搭配」里查看、编辑、删除，冷启动重开每个席位的单品与服务端一致；

删除搭配不影响衣橱；两个账号的候选与搭配互不可见，直接访问他人搭配 ID 得到 404。

**本轮最重要的判断**：**没有改后端**。`OutfitItem.layer_type` 看起来是"哪个席位"的现成字段，
但 API 里**没有任何写入路径**，所以席位改为由衣物自身的 `type` 按仓库自己的 `ITEM_ROLE` 表推导
（§2 有实测证据）。这样冷启动、编辑、Web 端读同一套搭配得到的席位天然一致，也不需要迁移。

## 2. 真实接口与数据模型（本轮实测，不是推断）

### 2.1 模型（`backend/app/models/outfit.py`）

* `Outfit`：`occasion`（必填，`String(50)`）、`name`（`String(100)`，可空）、`status`、`source`、
  `scheduled_for`、`weather_data`、`reasoning`/`style_notes`/`palette`/`notes`、时间戳。
* `OutfitItem`：主键 `(outfit_id, item_id)`，即**同一件衣物不能在一套搭配里出现两次**；
  另有 `position: int`（非空）与 `layer_type: String(20)`（可空）。

### 2.2 本轮用到的端点（都用 curl 对真实后端跑过，见 §5.1）

| 方法 | 路径 | 关键语义（实测） |
| --- | --- | --- |
| `POST` | `/outfits/suggestions` | 201；`items` 1..20、`occasion` ∈ `VALID_OCCASIONS`；`source=external`、`status=pending`、**不写 feedback**；`position` 按请求顺序；`layer_type` 为 `null` |
| `GET` | `/outfits?page&page_size&search` | 返回 `outfits/total/page/page_size/has_more`，仅本人的搭配 |
| `GET` | `/outfits/{id}` | 他人 id → 404 `OUTFIT_NOT_FOUND` |
| `PATCH` | `/outfits/{id}` | 只接受 `name` / `items`；`{}` → 400 `PATCH_EMPTY`；**`items` 是整体替换**，`OutfitItem` 被删除重建；已穿着（`feedback.worn_at`）→ 409 `OUTFIT_WORN_IMMUTABLE`；非本人 → 404 |
| `DELETE` | `/outfits/{id}` | 204；只删搭配行，不碰衣物 |
| `GET` | `/items?type=…&is_archived=…&search=…` | 席位的候选衣物；`type` 是**单个精确匹配**，没有多类型/角色过滤 |
| `GET` | `/items/types` | 未归档衣物按类型的计数（一次请求拿到全部类型计数） |

`POST`/`PATCH` 的 schema 都设了 `extra="forbid"`：多一个键就是 422（实测把 `layer_type`
塞进请求体 → `422 extra inputs are not permitted`）。

### 2.3 为什么席位是"推导"而不是"存储"（本轮的核心判断）

`layer_type` 存在、也会在 `OutfitItemResponse` 里返回，但**没有任何写入口**：

1. `SuggestionCreateRequest` 只有 `items: list[UUID]`，`ExternalOutfitService._persist_outfit`
   插入 `OutfitItem` 时不设置 `layer_type`；
2. `StudioCreateRequest` 同样，而且它会用 `_order_items_canonically` 丢掉调用方给的位置；
3. `PatchOutfitRequest` 只有 `name`/`items`，而 `StudioService.patch_outfit`
   **先删掉全部 `OutfitItem` 再重建**——即使有别的办法写进去，第一次编辑也会被抹掉。

所以本轮把"席位"定义成衣物 `type` 的函数，用仓库自己的 `ITEM_ROLE`
（`backend/app/utils/clothing.py`，Web 端 `frontend/lib/studio/canonical-order.ts` 是同一张表）：

```
base_top → 上衣    bottom → 下装    footwear → 鞋子
mid_layer + outer_layer → 外套      socks + neckwear + accessory → 配饰
full_body（连衣裙/连体衣）→ 无席位（本轮明确不支持）
无角色（unknown / other / suit）→ 无席位（提示待分类，绝不塞进上衣）
```

这张表是严格划分：每个 `type` 恰好一个角色，每个角色映射到至多一个席位。因此

* 冷启动后从 `GET /outfits/{id}` 重建的席位 = 保存时的席位（没有第二个字段需要同步）；
* `PATCH` 整体替换 `items` 不会丢席位（席位从来就没有单独存过）；
* Web 端读同一套搭配会得出同样的席位。

**没有做的兼容扩展**：原本可以给请求 schema 加一个"每件衣物的席位"字段，但那要动共享后端，
而且不改 `patch_outfit` 照样会被编辑抹掉——本轮证明不需要，故不改。

`ITEM_ROLE` 的三份拷贝不会漂移：`mobile/scripts/verify/outfit-slot-map.mjs` 直接解析
backend / Web / mobile 三个文件并逐键比对（§5.1）。

### 2.4 其它实测事实（影响实现的）

* **归档的衣物无法进入搭配**：归档会把 `status` 设为 `archived`，而
  `validate_item_ownership` 要求 `status == ready`，所以 `POST /outfits/suggestions` 加一件
  已归档衣物得到 403 `OUTFIT_ITEM_OWNERSHIP`（§5.1 第 19 组）。客户端因此把候选限定为
  未归档衣物，并且在保存遇到 403 时提示"可能已归档或正在识别中"。
* **衣物被删除**：`outfit_items.item_id` 是 `ON DELETE CASCADE`，删除衣物会让它从搭配里消失；
  客户端不补位、不伪造（搭搭配详情只渲染服务端返回的单品）。
* **`occasion` 必填**：本轮表单不问场合，保存时固定发送 `casual`（`VALID_OCCASIONS` 之一，
  已实测被接受）。这是一个**刻意的取舍**，没有假装用户选过它；详情页把它按服务端返回值显示。
* **没有幂等键**：`SuggestionCreateRequest` 只有搭配自身字段，因此超时后结果不确定，客户端
  不能声称成功，也不能承诺重试不会产生第二套搭配（§4.3）。

## 4. 三个步骤对应的行为与实现要点

### 4.1 滑动只影响目标席位

草稿是 `selection: Partial<Record<SlotKey, Item>>`：换一个席位就是改写一个键，
所以"只替换当前槽位"是数据结构保证的，而不是手势代码的巧合。设备上实测：
连续两次左滑后上衣从 `r3-上衣批量-13-*` 变成 `r3-上衣批量-12-*`，而下装仍为空
（`PASS s9-swipe-isolation`）。

### 4.2 面板：搜索与分页都是真的

`GET /items` 的 `type` 是单值精确匹配，席位是多个类型的集合（上衣有 7 个类型），
所以候选是**按类型逐页取完再合并**，不是"每种类型第一页"。面板再把完整集合按 12 件一屏展开，
并显示"已显示 N / M 件"。设备实测：上衣席位 15 件候选 → 打开面板显示 `已显示 12 / 15 件`
→ 点「加载更多」变成 `已显示 15 / 15 件`（`PASS s9-panel-pagination`）。
搜索走服务端（`search` 同时匹配名称/品牌/类型/备注），实测在下装面板搜 `skirt` 只剩半裙。

### 4.3 保存失败与"结果不确定"

* 保存失败时**草稿保留**，可以修改后重试（`PASS s11-save-failure`、`s11-save-keeps-draft`、
  `s11-save-retry`）。文案只声明界面事实（"已选好的单品仍在这里"），不声明服务端状态。
* **风险提示**：只有一种写入失败能证明"没有写入"——请求根本没发出去（未配置后端地址）。
  其余（超时、连接被断开、响应体没读完）都无法证明，因为 RN/Expo 对"从未连上"和
  "已送达但应答丢失"抛的是同一个错误。这些情况统一按「保存结果不确定…服务端可能已经保存，
  请先打开「已保存搭配」核对，不要直接重复保存，否则可能出现两套一样的搭配」处理；因为没有
  幂等键，这里**不承诺**重试安全（第三轮独立审查发现 B，修复见 §9.2）。
* 保存中按钮进入 loading（`disabled`），防连点。

### 4.4 归档 / 删除 / 无权限

* 候选只取未归档衣物；服务端另有 403 兜底。
* 详情页对"搭配里的单品是否还在衣橱"的判定改为**直接问服务端**：候选集合命中即视为在衣橱
  （该查询只含未归档衣物）；候选集合没有命中时，用 `GET /items/{id}` 查这一件单品——
  该端点不过滤 `status`/`is_archived`，所以答案是确定的。只有它返回 404 才显示
  「这件单品已不在衣橱里」，返回 200 则按 `status` 显示「已归档」「正在识别中」「识别失败」，
  查询失败或未知状态显示「未能确认这件单品是否还在衣橱里」。
  早先版本用的是"不在候选集合里 ⇒ 已归档"的推断，而候选集合会被 `MAX_PAGES_PER_TYPE` 截断、
  也会因为衣物改过类别而漏掉它，因此那个推断会误报（第三轮独立审查发现 C，修复见 §9.3）。
* 单品被删除时服务端级联删除关联行，界面只是少一件，不补位、不崩溃。

**已知设计取舍（非缺陷）**：

1. 席位由 `type` 推导：如果用户在衣橱里把一件衣物的类别从"毛衣"改成"大衣"，它在搭配里的席位

2. 保存时固定发送 `occasion=casual`（见 §6 第 6 项）。
3. 草稿不落盘：离开页面（或杀进程）会丢，因此有确认弹窗，但不做离线写入。
4. 候选加载：打开搭配页会为 5 个席位分别请求其类型（上衣 7 个类型 = 7 个请求，多数只需 1 页）。

## 9. 第三轮独立审查（`docs/第三轮-独立审查.md`）四项阻塞的修复

> 修复提交见 `docs/知衣-开发进度.md`；本节只记录"改了什么、凭什么说改好了、还差什么"。
> **本轮修复没有重跑设备套件、没有连真实后端、没有重新打包 APK**：下面的证据全部是在本机
> 对**真实源码**执行的离线检查（编译后调用真实模块）与源码断言；设备项与真实网络项见 §6 第 8–10 条。

### 9.1 发现 A：API 上限处静默丢弃原单品

* **根因**：`draftItemIds` 末尾 `slice(0, OUTFIT_MAX_ITEMS)` 静默截断；详情编辑保存发送该数组，
  而 `PATCH /outfits/{id}` 会删除并按提交数组整体重建 `outfit_items`，因此第 21 件单品与搭配的关联
  被删除，界面却报"保存成功"。文案「其他单品…保存时会原样保留」对同席位溢出也不成立。
* **修复**：
  1. `mobile/src/outfits/draft.ts`：`draftItemIds` 返回**全部** id，不再截断；新增
     `draftItemOverflow()`（`{total, excess, max}`）与 `draftBlocker()` 的 `'tooManyItems'`。
  2. `mobile/app/outfit/[id].tsx`：保存前检查超限 → 拒绝保存并给出具体数字；「其他单品」分组
     在编辑态显示同一数字，并提供**逐件**「从搭配中移除」（只删搭配关联，不删衣橱单品）。
     该分组同时按**当前席位选择**过滤：如果把「其他单品」里的那件选进了它自己的席位，它就不再列在
     这一组（否则该行会自称"同席位已有另一件"——已经不成立——而"移除"又只是删掉重复引用，像是没反应）。
  3. 新建 `passthroughReason()`：同席位重复 / 暂不支持席位（连衣裙、连体衣）/ 待分类 三种原因
     分开显示，不再把同席位冲突说成"待分类"。
  4. `mobile/src/i18n/zh.ts`：`othersNote` 改为真话（含 20 件上限），新增 `saveTooManyItems`、
     `removeFromOutfit`、`sameSlotDuplicate` 等文案。
* **证据**：`node scripts/verify/outfit-item-limit.mjs` — **35/35 通过**，其中包括审查用的
  最小复现（20 件 `shirt` + 1 件 `pants`）：`draftItemIds` 返回 21 件、`i19` 仍在数组里、
  `draftItemOverflow` = `{total:21, excess:1, max:20}`、`draftBlocker` = `'tooManyItems'`；
  并断言源码里不再出现 `slice(0, OUTFIT_MAX_ITEMS)`、两条保存路径都先查上限、其他单品按当前席位过滤。

### 9.2 发现 B：非超时传输失败也被当成"一定没写入"

* **根因**：`client.ts` 只把 `AbortError` 标为 `timedOut`，其余 `fetch` 拒绝一律
  `NetworkError(timedOut=false)`，界面据此断言"没保存"；`response.text()` 的失败甚至不在任何
  `try` 里，会漏成裸 `TypeError`。RN/Expo 对"从未连上"和"已送达但应答丢失"抛同一个错误，
  客户端无法证明未提交，而 `POST /outfits/suggestions` 没有幂等键。
* **修复**：`NetworkError` 改为携带 `outcomeUnknown`（默认 `true`）。只有**请求确实没发出去**
  （未配置后端地址，两条 `!apiBaseUrl` 分支）才 `false`；超时、连接中断、响应体读取失败
  全部为 `true`。新增 `readResponseBody`/`readResponseBodyOrNull`：4xx/5xx 的响应体读不到时
  仍按状态分类（服务器已拒绝 ⇒ 写入未生效），而**成功**响应的响应体读不到则归为结果不确定。
  两个保存界面改为按 `outcomeUnknown` 分支：不确定时显示"保存结果不确定 + 可能已保存、
  先看已保存搭配"，删除同样区分（`deleteUncertain`）。**编辑页用单独的措辞**
  （`saveUncertainEditMessage`）：`PATCH` 是替换这一套搭配、重试不会产生第二套，因此不沿用
  新建页那句"可能出现两套一样的搭配"。
* **证据**：`node scripts/verify/write-outcome-uncertainty.mjs` — **51/51 通过**。该脚本把真实
  `src/api/client.ts` 用项目自带 tsc 编译后调用真实 `request()`，用替身 `fetch` 复现：
  派发后抛 `TypeError('Network request failed')` → `NetworkError(outcomeUnknown=true, timedOut=false)`；
  响应体读取失败 → 同样 `outcomeUnknown=true`；未配置地址（子进程，`fetch` 调用次数为 0）→
  `outcomeUnknown=false`；403/409/422/500 一律是 `ApiError` 且不带不确定标记；调用方取消仍原样抛出；
  并断言新建页保留"可能两套"的警告、编辑页不出现该句。

### 9.3 发现 C：候选截断时误报"已不在衣橱"

* **根因**：详情页只读席位行用"单品不在该席位候选集合里 ⇒ 已归档"推断；候选集合按
  `MAX_PAGES_PER_TYPE` 截断（每类型 5 页 × 100），且衣物改过类别后会从旧席位的类型集合里消失，
  两种情况都会误报。
* **修复**：新建 `mobile/src/outfits/garmentAvailability.ts`（纯函数决策表）。候选集合命中
  ⇒ 在衣橱（该查询只含未归档衣物）；未命中 ⇒ 用 `GET /items/{id}`（`ItemService.get_by_id`
  只按 id + 归属过滤，不过滤 `status`/`is_archived`）查这一件：404 ⇒「已不在衣橱」，
  `archived` ⇒「已归档」，`processing`/`error` ⇒ 对应提示，其余未知 ⇒「未能确认…」。
  详情页 `ReadOnlySlotRow` 按该决策表渲染。
* **证据**：`node scripts/verify/garment-availability.mjs` — **25/25 通过**，含审查场景
  "候选被截断 + 该单品仍 `ready`" ⇒ 不显示"已不在衣橱"；以及"查询失败/未作答" ⇒「未能确认」，
  并断言详情页已不再有 `notInWardrobe` 推断。

### 9.4 发现 D：业务 403 被当成凭证失效并清除登录态

* **根因**：`errors.ts` 把**所有** 403 归为认证失败（`AUTH_FAILURE_STATUSES = {401, 403}`），
  `client.ts` 调用全局登出处理器，`AuthContext` 清 token、SecureStore 与查询缓存；因此
  `PATCH` 的 `403 OUTFIT_ITEM_OWNERSHIP` 会把人踢下线并丢掉草稿，编辑页自己的 403 提示永远不执行。
* **修复**：真实后端只在凭证无效时返回 401（`backend/app/utils/auth.py` 的 `decode_token` /
  `get_current_user`）；业务 403 一律带 `detail={error_code,message}`。因此
  `AUTH_FAILURE_STATUSES` 收窄为 `{401}`，新增 `isAccountLevelForbidden()`：只有 detail 等于
  `"User account is inactive"`（`get_current_user` 对停用账号的 403）才算凭证失效。
  `isCredentialRejection(status, credentialChecked, body)` 接收响应体；`/auth/session`
  （唯一 `credentialChecked: true`）仍按 401/403/422 处理。
* **证据**：`node scripts/verify/auth-status-policy.mjs` — **33/33 通过**（脚本已按新策略重写：
  断言业务 403 不再触发登出、停用账号 403 仍触发、422 规则保持第二轮修复后的行为，并断言
  `client.ts` 两个路径都把响应体交给同一判定、两个搭配界面仍以 `ApiError 403` 呈现业务拒绝）；
  `write-outcome-uncertainty.mjs` 另外用真实 `client.ts` 断言：业务 403 → `ApiError` 且
  登出回调 **0 次**，`"User account is inactive"` 403 → `AuthError` 且回调 1 次，401 → 1 次，
  普通 422 → 0 次。
