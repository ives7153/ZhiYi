## 2. 有证据的必须修复问题

### A. 达到 API 上限后编辑会静默丢掉原单品

`backend/app/api/outfits.py:583-587,1276-1280` 允许 1–20 件，且不限制同一席位的件数；`backend/app/api/outfits.py:349-364` 从衣物**当前**类型重建返回值，所以修改类别也可能造成同槽。`mobile/src/outfits/draft.ts:69-83` 在冲突时把第二件放入 `passthrough`，通常不会丢；对两件同槽（`shirt`、`t-shirt`）实际运行该函数，`draftItemIds` 仍返回两件。不能把一般同槽冲突本身说成“打开就丢”。

但 `draftItemIds` 在 `mobile/src/outfits/draft.ts:160-179` **无提示地** `slice(0, OUTFIT_MAX_ITEMS)`；详情编辑保存总发送该数组（`mobile/app/outfit/[id].tsx:116-135`），服务端 `StudioService.patch_outfit` 在 `backend/app/services/studio_service.py:395-415` 删除旧关联并用提交数组整体重建。对真实函数的最小复现：服务器原有 20 件 `shirt`（首件占上衣，其余 19 件留在“其他单品”），编辑时在空下装槽加入一件 `pants`，草稿共 21 件，请求只含 20 件，原第 20 件 `i19` 被无提示排除。若服务端正常接受，原单品的搭配关联将被删除。需在溢出时阻止保存并明确告知用户处理，或提供不丢原件的编辑方式；不应静默截断。现有“其他单品不属于本轮席位，保存时会原样保留”（`mobile/src/i18n/zh.ts:250-251`）对同槽溢出也是不实描述，须明确冲突/不可编辑边界。此用例未请求真实后端或操作设备；最终删除结果由确定的客户端请求内容与服务端整体替换实现推导。

### B. 非超时传输失败也可能发生在服务端提交之后

`mobile/src/api/client.ts:124-149` 只把 `AbortError` 标为 `timedOut=true`，任何其他 `fetch` 拒绝均转成 `NetworkError(timedOut=false)`，读取 `response.text()` 的失败甚至不在捕获范围。`mobile/app/(tabs)/outfits.tsx:124-137,239-265` 只对 `timedOut=true` 展示“结果不确定/先查已保存”，其余显示普通保存失败并允许再次保存；报告 §3.3 把非超时网络错误解释为“一定没写入”。实际模块的模拟：使 `fetch` 在模拟服务端已写入后抛 `TypeError('Network request failed')`，得到 `NetworkError(timedOut=false)`；令已到达的响应在 `text()` 中断则透出 `TypeError`。请求发出后客户端无法凭异常类型证明事务未提交；`POST /outfits/suggestions` 无幂等键（`backend/app/api/outfits.py:583-603`），直接重试可能重复创建。应对无法确认请求未送达的写入失败统一提示结果不确定、先查列表；只有有证据表明请求未发送/被拒绝连接时才能断言未保存。模拟验证的是分类路径，不声称已在真实移动网络制造该时序。

### C. 候选截断时误报“已不在衣橱”

`mobile/src/api/outfits.ts:107-174` 每类型最多加载 5 页 × 100 件，并返回 `truncated`。详情只读行 `mobile/app/outfit/[id].tsx:456-460,500-504` 在候选请求成功但缺少当前 ID 时就显示“这件单品已不在衣橱里（可能已归档）”，**没有检查** `candidates.truncated`。例如某类型中仍未归档、在第 501 件的搭配单品：候选成功但被截断，详情会作出错误结论。`useSlotCandidates(slot, '')` 固定空搜索（`[id].tsx:456`），搜索面板的筛选是独立 query key（`outfitHooks.ts:61-71`），故**当前详情误报不由面板搜索触发**；首次加载失败也没有 `isSuccess`，不会单凭失败报归档。需只在候选集合完整时作此推断，或按单品 ID 直接查询状态；截断/未知要明确写“未能确认”，不要判定已离开衣橱。此为条件分支的静态证明，未构造 501 件设备数据。

### D. 业务 403 被统一层当作凭证失效并清除登录态

真实服务端 `backend/app/api/outfits.py:632-639,1479-1486` 会对衣物无所有权/不可用返回 `403 OUTFIT_ITEM_OWNERSHIP`；`backend/app/services/studio_service.py:50-70` 的有效性检查与登录凭证无关。但 `mobile/src/api/errors.ts:73-91` 将所有 403 归为认证失败，`mobile/src/api/client.ts:159-170` 调用全局处理器并抛 `AuthError`；`mobile/src/auth/AuthContext.tsx:89-109` 会清内存 token、SecureStore 凭证和查询缓存。因此创建/编辑页自己的 `ApiError && status===403` 提示（`outfits.tsx:131-135`、`[id].tsx:150-153`）不会执行。实际请求模块模拟业务 403 得到 `AuthError` 和一次登出回调；现有 `auth-status-policy.mjs` 也明确断言一般请求 403 是认证错误（本次执行 21/21 通过，说明脚本覆盖了错误的策略而非排除了本缺陷）。需区分业务 403 与真正凭证拒绝，只对经确认的认证失败清除凭证；保存业务错误应保留当前登录及草稿并呈现可操作提示。

## 3. 可后续优化（非上述缺陷的修复替代品）

- 同槽冲突目前可见于“其他单品”并在不超限时随保存保留，但被标作“不属于本轮席位”或“待分类”（`[id].tsx:289-335`），实际同槽衣物并非待分类；可专门展示冲突成因及可操作性。此项文案/编辑体验本身不等于“两件普通同槽衣物必然丢失”。
