## 3. 必须修复的问题

### M1（产品 · 中）添加成功面板裸露后端枚举 `unknown` —— C17 只修了一半

* **位置**：`mobile/app/item/new.tsx:575` → `{item.name || item.type}`
* **触发条件**：添加衣物时**不填名称**（名称是选填，界面自己写着“都可以稍后修改”），即最普通的一条路径。
  服务端 `name` 保持 `NULL`，`type` 保持 `'unknown'`（或用户选的 `shirt`、`bag`…）。
* **实测证据**（我的原始产物，均在临时目录）：
  * UI dump `review-artifacts/unnamed-02-after-submit.xml` 的可见字符串是：
    `已添加` / `这件衣物已经可以使用了。` / **`unknown`** / `查看这件衣物` / `返回衣橱` / `添加`；
    截图 `unnamed-02-after-submit.png`（1080×2400）。
  * 同一时刻服务端该行：`{'name': None, 'type': 'unknown', 'tagging_status': 'pending', 'status': 'ready'}`。
  * 复现：登录后 → 添加单品 → 从相册选择 → **不填名称** → 点「添加」→ 看成功面板。
* **影响**：中文界面里直接出现英文后端枚举；这正是本轮宣称已修好的验收项
  （C17“界面不显示内部状态枚举”，以及 `src/i18n/zh.ts` 顶部“用户可见文案不得包含后端状态值”的规则）
  在**最常用流程**上的漏网。它不是风格问题——是同一轮里“已修 / 未修”自相矛盾的用户可见缺陷。
  现有脚本抓不到它：s1 特意输入了名称、s4 只比较服务端计数、s2 的枚举扫描只扫**详情页**。
* **建议修法**（一行 + 一句断言）：
  1. `import { clothingTypeLabel } from '../../src/api/itemVocab';` 后改为
     `{item.name || clothingTypeLabel(item.type) || zh.wardrobe.unnamedItem}`（与 `ItemCard` 的兜底口径一致）；
  2. 顺手把成功面板纳入枚举扫描：在 s1（或 s2 增加一步）断言成功面板的可见字符串**不含**
     `unknown|shirt|top|coat|pants|dress|skirt|bag|…` 一类 token，避免同类漏网再发生。

### M2（脚手架 · 中）验收脚本不校验“App 当前登录的是哪个账号”，**已实测出错误账号上的 PASS**

* **位置**：`mobile/scripts/run-acceptance.sh`
  * `login_dev()`（:349-386）——只要 App 已在衣橱页就打印 `already logged in (session restored from secure storage)`
    并**直接返回成功**，**从不校验当前会话属于 `$TEST_USER_EMAIL`**；
  * `scenario_s5()`（:1014-1082）——判据是“看不到登录页 + 衣橱页 +（`$name` 可见 **或** `衣柜中有 $count 件单品`）”，
    而 `$name` / `$count` 全部取自 **`$TEST_USER_EMAIL`** 这个账号的 API；
  * `scenario_s1` / `scenario_s4` —— 只比较配置账号的服务端计数。
* **实测证据 A（误导性 FAIL）**：第一次我用 `TEST_USER_EMAIL=review-124937@zhiyi-review.com` 跑 s1，
  而设备当时登录的是 `harness@zhiyi-harness.com`：
  ```
  ==> already logged in (session restored from secure storage)
  FAIL   s1-add-from-gallery    no new item appeared on the server within 45s (before=0 after=0)
  ```
  但同一屏的 dump 写的是 `这张照片已存在` / `衣橱里已经有这张照片了，没有重复添加。`——即
  **产品行为完全正确**（照片在该账号里已存在 → 服务端 409 → 不重复入库），报错信息却指向“没上传成功”。
  两个账号的 `/items` 计数分别是 `0`（我的新账号）与 `1`（harness 账号），坐实了“账号错位”。
* **实测证据 B（错误账号上的 PASS）**：把两个账号都造到**各 1 件**、设备登录 **harness 账号**，
  再以 `TEST_USER_EMAIL=review-124937@…` 跑 s5：
  ```
  PASS   s5-cold-start   3/3 cold starts restored the session and re-read the wardrobe from the backend
     ok cold start 1/2/3: wardrobe rendered with the server's count (1)
  ```
  —— 3 次“通过”读到的**全是 harness 账号的数据**（`$name` 没出现，于是退化到计数分支，而计数恰好相等）。
* **影响**：这是“没被测到也算通过”的一类空过。它不但让**报告里的 s5 记录无法证明“恢复的是谁的会话”**，
  更危险的是对下一轮的连带效应：s5 式的“名字不可见就退化为计数”判据一旦复用，
  **别人的搭配数据可能被当成自己的通过**。另外它会给未来任何账号不一致的运行留下**指向错误原因**的 FAIL。
* **建议修法**：
  1. 在 `main()` 里加“账号一致性”前置断言：进入场景前读取 App 的当前身份（读 `我的` 页邮箱文本即可），
     与 `$TEST_USER_EMAIL` 比对；不一致就**先用 App 自己的退出登录再登录**，否则直接 FAIL 并打印双方账号；
  2. `s5` 判据收紧为“必须看到 `$TEST_USER_EMAIL` 的物品名”（计数兜底只在**账号已确认**的前提下保留），
     避免“名字不可见 → 计数巧合相等 → PASS”；
  3. 顺手让 `login_dev` 把读到的当前邮箱打进日志，事后凭记录即可判断跑的是谁。

## 6. 结论

**先修复以下问题**：

1. **M1**：`app/item/new.tsx:575` 成功面板的 `item.name || item.type` 会在“不填名称”这条主路径上把
   `unknown`（或 `shirt` 等）直接显示给用户 —— 本轮 C17“界面不显示后端枚举”的修复漏了这一处；
   建议用 `clothingTypeLabel()` 兜底并把成功面板纳入枚举扫描。
2. **M2**：`run-acceptance.sh` 不校验 App 当前登录账号 → 已实测出“**在别的账号上判 PASS**”（s5）
   与“**把 409 重复误报成上传失败**”（s1，且产品行为其实正确）；建议加账号一致性前置断言，
   并把 s5 的判据从“名字不可见就退化为计数”收紧。

除这两项外，本轮的产品主张我都独立复现通过：**上传 / 编辑（含不伪造人工分类）/ 冷启动 3/3 /
防重复 / 归档可逆 / 删除 / 失败保留输入与重试 / 缓存自动刷新 / 跨用户隔离 / 35 项接口契约 /
无 Metro 桌面启动 / APK 版本签名与覆盖升级**；APK 与当前 HEAD 的对应关系成立（结构级证据，
且交付包在真机上原样复现了 M1，反向印证“包 = 代码”）。

第三轮的搭配功能尚不存在，因此“槽位切换、搭配保存、编辑搭配、搭配的跨用户隔离”**本轮无从审查**，
不在“通过”之列；实现后应沿用本报告 §2.5 与 §3-M2 的口径重新验证隔离与判据。

> 本报告只新增 `docs/独立审查.md`；产品代码、配置、依赖、签名、设备数据（未卸载、未 `pm clear`）均未改动。
