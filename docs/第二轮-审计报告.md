## 4. EXIF 方向：C5 被证伪，C6 理由需改写

### 4.1 我读到的原文（第一手）

`mobile/node_modules/expo-image-picker/android/src/main/java/expo/modules/imagepicker/ImagePickerUtils.kt`

```
202: internal suspend fun copyExifData(
212:   val omittableTags = listOf(
213:     ExifInterface.TAG_IMAGE_LENGTH,
214:     ExifInterface.TAG_IMAGE_WIDTH,
215:     ExifInterface.TAG_PIXEL_X_DIMENSION,
216:     ExifInterface.TAG_PIXEL_Y_DIMENSION,
217:     ExifInterface.TAG_ORIENTATION        ← 关键
218:   )
225:     .filter { (_, tag) -> !omittableTags.contains(tag) }
228:     .forEach { (tag, value) -> targetExif.setAttribute(tag, value) }
```

`TAG_ORIENTATION` **在排除列表里**。同时
`exporters/CompressionImageExporter.kt:53-63` 用 `loadImageForManipulationFromURL`
（`expo-image-loader/.../ImageLoaderService.kt:73-78` 走 Glide `asBitmap()`）解码 —— Glide 确实应用
EXIF 方向，但方向标签**不会再被写回**。

`exporters/RawImageExporter.kt:14` → `MediaHandler.kt:50`：`quality == 1.0`
（`ImagePickerConstants.MAXIMUM_QUALITY`）走 `RawImageExporter`，**直接字节复制，源 EXIF 完整保留**。
客户端当前用的正是 `quality: 1`（`photoPicker.ts:159`），即这条路径。

### 4.2 我的端到端实测（真实后端 + 真实数据）

### 4.3 结论与必须的修正

### B-2（中）编辑名称会「静默把衣物标注为已完善」并可能清掉类别 — 且源码注释与事实相反

`app/item/[id].tsx` 的 `EditForm.submit()` 无条件发送 `type: type ?? 'unknown'`（第 435 行），
且用户未选类别时 `type` 为 `null`。后端把 `type` 视为**标注写回字段**：

```
backend/app/api/items.py:1252
if any(_has_tag_content(f, update_data.get(f)) for f in TAG_WRITEBACK_FIELDS):
    item.tagging_status = TaggingStatus.tagged
    item.tagged_by = TaggedBy.manual
```

我的实测（真实后端）：

```
before: type= unknown  tagging= pending  tagged_by= None
after : type= unknown  tagging= tagged   tagged_by= manual
# PATCH body: {"type":"unknown","name":"改名而已","brand":null,"colors":[],...}
```

我用真实后端确认：`TAG_WRITEBACK_FIELDS` 是 `{"type","subtype","colors","primary_color","tags"}`，
而 `_has_tag_content` 对字符串判断 `value not in (None, "", [], {})`。**`"unknown"` 不在其中
⇒ 只要提交里带了 `type`，即使值是 `"unknown"`，也会把物品标记为「已完善 / 人工标注」。**

而 `src/api/itemWrites.ts:131` 的注释写着：

> `Editing a name alone does not.`（只改名称不会触发写回）

**这句话在客户端实际发出的请求下是错的** —— 因为客户端在「只改名称」时也会附带 `type: 'unknown'`。

> **影响**：用户在**从未选择类别**的情况下只改一个名字，衣物的「标注状态」会从「待完善」
> 变成「已完善」，且 `tagged_by=manual`，这会让后续 AI 打标（`workers/tagging.py:277` 只在
> `was_pending` 时写入 `tagged_by/tagged_at`）不再补全标注。同时若物品原类别是 AI 打出的 `shirt`，
> 用户在编辑页看到 `null` 并保存，**类别会被 `'unknown'` 覆盖**，列表筛选随之变化。
>
> **裁决**：**非阻塞但应修**。修法二选一：(a) `EditForm.submit()` 只在用户真的改过/选过类别时才带 `type`
> （推荐，符合「`unknown` 不是用户选择」的原意）；(b) 修正 `itemWrites.ts:131` 的注释，并在 UI 上
> 让「未选择」与「已确认无类别」可区分。至少必须让注释与行为一致。

### B-5（中）`run-acceptance.sh` 的 s4 存在「空过即 PASS」路径

