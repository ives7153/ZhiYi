## 3. 服务端接口契约（我在本机**亲自复测**的结果）

### 3.1 认证

```
$ curl -s -X POST .../api/v1/auth/sync -H 'Content-Type: application/json' \
    -d '{"external_id":"dev-leader-verify2","email":"dev@example.com","display_name":"Dev User"}'
{"id":"1b66f608-...","email":"dev@example.com","display_name":"Dev User",
 "is_new_user":true,"onboarding_completed":false,"access_token":"eyJhbGciOiJIUzI1NiIs..."}

$ curl -s .../api/v1/auth/session -H "Authorization: Bearer $T"     → HTTP 200，返回 UserResponse
$ curl -s .../api/v1/users/me       -H "Authorization: Bearer $T"   → HTTP 200，返回用户资料
```

JWT：`alg=HS256`，`sub` = `external_id`，**有效期 7 天**。**无 refresh 端点**（已全仓确认）。

**移动端回调实测**：

```
$ curl -s -o /dev/null -D - ".../api/v1/auth/mobile-callback?code=abc123&state=xyz"
HTTP/1.1 302 Found
location: wardrowbe://auth/callback?code=abc123&state=xyz
```

→ `app.json` 的 `scheme` 必须是 `wardrowbe`（已确认一致）。服务端 `MOBILE_APP_SCHEME = "wardrowbe"` 是硬编码的。

### 3.2 401 契约（实测状态码 + body）

| 场景 | 状态码 | body |
| --- | --- | --- |
| 无 token | 401 | `{"detail":"Not authenticated"}` |
| 坏 token | 401 | `{"detail":"Invalid or expired token"}` |

→ 客户端判登录失效应**以状态码为准**，不要依赖 `detail` 文本。

### 3.3 ⚠️ 一个真实陷阱：`.local` 邮箱的 422

`UserSyncRequest.email` 是宽松 `str`，但 `UserResponse.email` 是 `EmailStr`。

实测（用户 email = `probe@wardrobe.local`）：

| 端点 | 结果 |
| --- | --- |
| `/auth/session` | **HTTP 422** `{"detail":"Validation error","errors":[{"field":"email","message":"...special-use or reserved name..."}]}` |
| `/users/me` | HTTP 200 ✅ |
| `/items` | HTTP 200 ✅ |

即：`.local` 能成功建号，但 `/auth/session` 会 422，而 `/users/me` 与 `/items` 仍正常 200 ——
**只按 401 判失效的客户端会卡在「已登录但校验不过」的诡异状态**。

处理要求（已写进规格与客户端）：
1. 开发登录表单**不预填** `.local` 邮箱（Web 端默认值是 `dev@wardrobe.local`，移动端**不要照搬**）；
2. 把 **422 与 401/403 一并视为「凭证不可用」**，走清除凭证 + 回登录页。

### 4.5 认证状态机

- 冷启动：读安全存储 token → 调 `/auth/session` → 200 恢复；401/403/422 清除凭证 → 登录页。
- 凭证：`access_token` **只进 `expo-secure-store`**；仅非敏感的 `id/email/displayName` 进 `AsyncStorage`。
- 登出：`clearAllCredentials()`（清 token + profile）+ `queryClient.clear()`（清**上一个用户**的全部缓存）。
- **无静默刷新**：服务端没有 refresh 接口，401 一律强制重新认证，绝不循环重试。
- OIDC：Authorization Code + PKCE，**公共客户端无 client_secret**，scheme = `wardrowbe`；
  仅当 `/auth/config` 返回 `oidc.enabled === true` 时才渲染 OIDC 按钮，
  仅当 `dev_mode === true` 时才渲染开发登录表单（读取服务端配置，不是构建期常量）。

### 4.6 统一请求封装

- 单一 `request()`：`EXPO_PUBLIC_API_URL`（**不含** `/api/v1`）+ `/api/v1` + path。
- `AbortController` 超时（15 秒），超时文案可读。
- 三类错误：`NetworkError`（连不上/超时）、`AuthError`（401/403/422，触发全局登出）、`ApiError`（其余 4xx/5xx，读 `detail`）。
- 图片 URL：`joinUrl()` 处理「返回值已含 `/api/v1` 而基址不含」的错位，
  **不会**产生 `/api/v1/api/v1/...`；绝对 URL 原样透传；回退顺序 thumbnail → medium → image → 占位块。
- 缓存 `staleTime` = 60 秒（**小于**签名 URL 的 1 小时有效期，保证能刷新签名）。
- 所有 `queryKey` 以 `userId` 开头，实现用户隔离。

## 12. 第二轮：实现要点（与规格逐条对应）

### 3.1 衣橱页：分类、搜索、筛选、分页、下拉刷新、详情

- 搜索、类别筛选、只看收藏、只看需清洗、排序（最近/最早/名称）**全部走服务端**参数。
  客户端过滤只会过滤「已加载的那几页」，那是个假象，所以没那样做。
- 分页沿用 `useInfiniteQuery`（`page` 从 1 开始，`has_more` 决定是否续拉）。
- 下拉刷新用 `RefreshControl`；`refreshing` 绑到真实的 `isRefetching`，不假转。
- **回到页面即刷新**（`useFocusEffect`）：从添加页/详情页返回后列表不会停在旧数据。

### 3.2 拍照与相册

- `launchImageLibraryAsync` / `launchCameraAsync`，`mediaTypes: ['images']`。
- **取消选择**：`canceled: true` 是正常操作，**不报错、不提示**，直接回到空闲态。
- **权限**：区分「可再次询问」与「已被永久拒绝」；后者文案指向系统设置。
  相册权限被拒但系统 PhotoPicker 仍可用时不误报（API 33+ 的相册选择器本身不需要运行时权限）。
- **大小与压缩**：统一重编码为 JPEG，长边 ≤1600、质量 0.8。
  依据：服务端 `validate_image` 拒绝 >20MB，`_open_bounded` 拒绝 >`max_image_megapixels`(50MP)。
- **格式限制以真实接口为准**：客户端只放行服务端 `ALLOWED_MIME_TYPES` 允许的
  JPEG/PNG/WebP/HEIC；不确定时以重新编码后的 JPEG 提交。

### 3.3 上传：

复用原后端接口（**没有新写上传接口**）：`POST /items`（单件）、`POST /items/bulk`（多件）。

| 需求 | 实现 |
| --- | --- |
| 适配 RN 的 multipart | `request()` 之外单列 `requestMultipart()`；**不手设 Content-Type**（boundary 必须由 fetch 生成） |
| 幂等键 | 复用服务端 `upload_keys`（`(user_id, upload_key)` 部分唯一索引），批量上传时逐个下发 |
| 不复制浏览器实现 | 没有移植 Web 的 `FormData`/IndexedDB 队列；Go 语义按服务端契约重写 |

### 3.4 上传/处理中/完成/失败，区分「上传成功」与「AI 识别成功」

客户端状态机：`idle → preparing → uploading → analyzing → saved | error`

- 文案区分：`正在上传照片...` vs `正在识别衣物信息...`（规格明确要求分开）。
- **是否进入 analyzing 由服务端返回的 `status` 决定**，不是客户端猜：
  `status === 'processing'` 才是后台识别中，否则直接告诉用户「已经可以使用了」。
- AI 未配置时服务端返回 `status: 'ready'`，界面就不会承诺一个永远不会发生的识别。

### 3.5 AI 关闭或失败时仍可手动维护

实测（AI 关闭）：`POST /items` → `status: "ready"`、`tagging_status: "pending"`。

- `ready` + `is_archived=false` 正是 `recommendation_service`/`pairing_service` 选择单品所需，
  所以**手动录入的衣物天然可被后续搭配使用**。
- `tagging_status: 'pending'` 表示仍可手动补充信息，界面显示「待完善」。
- 核对过处理状态与标注状态：**没有**任何绕过服务端校验的写法 ——
  客户端不发送 `status`，`ItemUpdate` 也不接受它（`type/name/brand/colors/...` 之外一律忽略）。
- 编辑 `type`/`subtype`/`colors`/`primary_color` 时服务端会自动置 `tagging_status='tagged'`、
  `tagged_by='manual'`（`TAG_WRITEBACK_FIELDS`），界面随之显示「已完善」。

### 3.6 详情与编辑；归档或删除前说明真实影响

两种销毁性操作的语义**不同**，界面文案按真实语义分别写（都从处理器代码读出，不是照按钮名写）：

| 操作 | 真实语义 | 界面文案要点 |
| --- | --- | --- |
| 归档 `POST /items/{id}/archive` | `is_archived=true`、`status=archived`；**行与图片都保留**；`outfit_items` 不动；`restore` 可恢复 | 「不再出现在衣橱列表里，也不会再被用于生成搭配。衣物和照片都会保留，随时可以取消归档。」 |
| 删除 `DELETE /items/{id}` | 删除行**并删除所有图片文件**；`outfit_items.item_id` 是 `ON DELETE CASCADE`，**会从已有搭配中移除** | 「衣物和它的所有图片都会被永久移除，也无法再恢复。已经用到它的搭配会一并移除这件衣物。」 |

保存后：服务端返回的对象**直接写入详情缓存**，同时使列表与分类计数失效 —— 详情不会闪旧值，
列表不会留旧值。

### 3.7 失败保留输入 + 防重复

- 失败时**只改阶段**，照片与全部已填字段原样保留；界面明说「照片和填写的信息都已保留」。
- 防重复是**两道**：
  1. `submittingRef` 同步锁 —— 同一帧内的第二下点击被直接丢弃；
  2. `isPending` 禁用按钮。
  （只靠 state 会漏掉同一帧的连点，所以锁必须是同步的。）
- 重复照片服务端返回 **409**，界面按「已存在」中性提示处理，**不**当作需要重试的错误。

### 3.8 图片 URL 的拼接、有效期与刷新

- 相对签名路径经 `joinUrl()` 拼绝对地址（基址不含 `/api/v1`，返回值含，**不会**拼成
  `/api/v1/api/v1/...`）；已是绝对地址则原样透传。
- 优先顺序 `thumbnail → medium → image → 纯色占位块`。
- 签名 1 小时过期；列表 `staleTime` 60 秒，回到页面即刷新，`processing` 时 5 秒轮询 ——
  所以签发会持续更新，重启后也能重新取到有效签名（已实测重启后图片正常）。

### 3.9 视觉与文案

- 沿用第一轮设计令牌（黑白简洁，与 Web 一致），未引入新色。
- 文案全中文、面向普通用户；**界面不出现内部枚举**：
  `ready/processing/error/archived/pending/tagged` 一律经 `zh.itemStatus` 映射为
  「可用/识别中/识别失败/已归档/待完善/已完善」。实测详情页显示的是「可用」「已完善」。
- 未加任何调试面板；token 仍只进 `expo-secure-store`。

## 14. 第二轮：发现并修复的缺陷

### 14.1 🔴 阻塞性：Expo SDK 57 的 `fetch` 不支持 `{uri,name,type}` 分片 —— 所有上传静默失败

**现象**：点「添加」后按钮永久 loading，最终显示「上传失败，请检查网络后重试。」；
**后端日志里完全没有 `POST /api/v1/items`**（GET 全部正常）。既不报错也无超时。

**根因**：`app.append('image', { uri, name, type })` 是 React Native 的经典写法，靠原生网络栈打开
本地文件；但 **Expo 替换了全局 `fetch`**，改用 JS 序列化 body。
`mobile/node_modules/expo/src/winter/fetch/convertFormData.ts` 的 `convertFormDataAsync`
只处理 `string` / `Blob` / 带 `bytes()` 的对象，其余一律
`throw new Error('Unsupported FormDataPart implementation')`；该函数注释原文：
「`uri` is not supported for React Native's FormData.」

因为异常在 `fetch` 内部抛出，**请求根本没发出去** —— 所以服务端无日志、客户端无超时，
两端都看不见真正的错。

**修复**：安装 `expo-file-system`（`~57.0.7`），用它的 `File` 类（`implements Blob`，有
`bytes()` / `type` / `size`）作为分片：
`form.append(field, file as unknown as Blob, photo.name)`。
这正是 `convertFormDataAsync` 接受的形状。见 `src/api/itemWrites.ts` 的 `appendFilePart()`。

**回归防护**：`mobile/scripts/verify/formdata-part-contract.mjs` 直接读 Expo 的序列化器源码来
断言这个契约（13 项）。将来 SDK 若再改变接受的分片形状，这里会先失败，而不是又落到设备上。

> **⚠️ 范围说明（两份报告曾看似矛盾，已弄清）**：
> 独立检索员的报告里写着「`{uri,name,type}` 是唯一正确写法、Blob 不支持」。那个结论**本身没错，
> 但它读的是 `NetworkingModule.kt`（React Native 的**原生**网络栈），而本仓库**不走那条路**。
>
> 决定走哪条路的是 `mobile/node_modules/expo/src/winter/runtime.native.ts:41-53`：
> 只有设置 `EXPO_PUBLIC_USE_RN_FETCH=1` 时 `fetch` 才回落成 RN 原生实现；
> **本仓库未设该变量**（`.env` / `.env.example` / `app.json` 均已确认），所以走 Expo 的 JS `fetch`。
>
> | | RN 原生（`USE_RN_FETCH=1`） | **Expo `fetch`（本仓库）** |
> | --- | --- | --- |
> | `{uri}` 分片 | ✅ 支持 | ❌ 抛异常 |
> | `Blob` / `File` 分片 | ❌ 不支持 | ✅ **唯一支持** |
>
> 两套写法**互斥**，不能混用。判断依据就是 `EXPO_PUBLIC_USE_RN_FETCH` 那一行。
> 检索员报告已补充 §12 专门说明这个边界。

**修复后实测**：`POST /api/v1/items HTTP/1.1" 201 Created`，衣物入库并可显示。

### 14.2 🟠 第一轮遗留：422 被一律当成「登录失效」

第一轮把 401/403/**422** 一律判定为凭证不可用并强制登出。那在只读的第一轮是合理的
（当时唯一的 422 来自 `/auth/session` 的 `EmailStr` 校验），但本轮有了写操作：
`POST/PATCH /items` 对**普通请求体校验失败**也返回 422。照旧规则，用户把衣物名多打一个字
就会被登出并清空缓存。

**修复**：拆成两件事（`src/api/errors.ts`）
- `isAuthFailureStatus`：只有 **401/403**，对所有端点成立；
- `isCredentialRejection(status, credentialChecked)`：仅当端点显式声明
  `credentialChecked: true`（目前**只有** `/auth/session`）时，422 才算凭证被拒。

这样既保住第一轮对 `.local` 邮箱的保护，也不会让写操作的校验错误变成登出。
回归测试：`auth-status-policy.mjs`（21 项），并验证只有 `/auth/session` 声明了该标记。

### 14.3 🟡 方向：机制描述曾过于绝对（已改正，行为未变）

**自我更正**：最初我把重编码的理由写成「picker 会抄回一个已被应用的 orientation 标签，直传
会被再转一次」。经检索员独立复核 + 读源码，**这个机制描述对 SDK 57 是错的**：
`ImagePickerUtils.kt:202-228` 的 `copyExifData` 把 `TAG_ORIENTATION` 列在 `omittableTags`
里，压缩路径不会写出旧标签；而 `quality:1` 走 `RawImageExporter` 是字节原样复制（像素未转正 +
标签保留），两者恰好互补，**四条真实进图路径实测落盘几何全部正确**：

| 路径 | 提交几何 | 落盘几何 |
| --- | --- | --- |
| `quality:1` 原样直传 | (1600,1200) + tag=6 | (1200,1600) ✅ |
| picker 压缩 `quality:0.6` | (1200,1600) 无标签 | (1200,1600) ✅ |
| `allowsEditing` 裁剪 | (1200,1600) 无标签 | (1200,1600) ✅ |
| manipulator 重编码 | (1200,1600) 无标签 | (1200,1600) ✅ |

四条 pHash 完全一致。**代码行为一直是正确的，改的是注释里错误的理由** ——
否则后来人会据此推出错误结论。重编码现在给出的理由是三条各自成立的：不依赖 `quality` 取值、
满足 20MB/50MP 硬限制、输出字节构造上 EXIF 干净。

`mobile/scripts/verify/exif-roundtrip.py` 刻画的是**后端链路本身**对每种输入的转正行为。
它手工构造三种输入，只看后端各自落盘的方向 —— 与 picker 无关：

```
A. no/1 orientation tag (manipulator output)  -> bar ON TOP (upright, correct)
   OK: backend leaves it upright.

B. tag=6 (rotate-90-CW already applied to pixels)
   declared size before transpose: (400, 300), as-would-be-displayed: (300, 400)
   backend exif_transpose result -> bar on RIGHT (image rotated 90 CCW vs expectation)
   BACKEND BEHAVIOUR: exif_transpose rotates it again, so a file of
   this shape would land rotated 90 deg relative to the photo. This
   fixture is hand-built and UNREACHABLE from the SDK 57 picker: its
   two exporters are complementary, so no real pick results in
   'pixels already upright + stale orientation tag'.

C. sideways pixels + correct tag=6            -> bar ON TOP (upright, correct)
   OK: a correctly tagged sideways photo is straightened.

PASS: the backend pipeline is characterised.
```

**注意 B 例读法**（本节此前正是在这里自相矛盾，现已删掉旧论证）：
B 例是手工构造的「像素已转正 + 仍保留 orientation 标签」组合，**SDK 57 的 picker 产生不出来**
（脚本尾部的 scope note 自己写明：「It does NOT show that the picker produces case B — it does not.」）。
所以这个脚本**不**证明「picker 会二次旋转」，也**不**充当重编码的理由。

客户端仍然统一用 expo-image-manipulator 重编码（其 Android 解码不读 EXIF、`Bitmap.compress`
不写 EXIF），上传的字节自洽 —— 与「压缩到长边 1600」是同一步。**理由是上一段的三条**，
不是「picker 输出方向有问题」：四条真实进图路径的落盘几何上表已实测全部正确。

> 上面这段是**本节唯一的结论**。曾在同一节里出现的旧说法
> （「picker 会把源 EXIF 复制到输出文件 → 直传会被再旋转一次」、
> 以及引用旧脚本输出的 `PASS: re-encoding before upload is the form that survives exif_transpose.`）
> **已被删除**，因为它与 `ImagePickerUtils.kt` 的 `omittableTags` 直接冲突。

### 14.5 🔴 编辑表单会把「只是改名」当成「人工分类」（独立审计发现，已修）

**这是本轮最严重的功能缺陷**，由审计员在对抗性复核中发现，我随后在真实后端上完全复现。

**问题**：编辑页的提交按钮**无论改了什么**都会发 `type: type ?? 'unknown'`。而服务端把
`type`/`subtype`/`colors`/`primary_color`/`tags` 的写入视为「人工分类」
（`TAG_WRITEBACK_FIELDS`），会随之把 `tagging_status` 置为 `tagged`、`tagged_by` 置为 `manual`。

实测（同一账号、同一件衣物）：

```
初始：                        type=unknown  tagging_status=pending  tagged_by=None
旧行为 PATCH {type:unknown, name:Renamed}
                          ->  type=unknown  tagging_status=tagged   tagged_by=manual   ❌
新行为 PATCH {name:Renamed}
                          ->  type=unknown  tagging_status=pending  tagged_by=None     ✅
```

即：**用户只是改个名字或点个收藏，衣物就会停止报告「待完善」，并谎称有人给它归过类。**
更糟的是如果原本 `type` 是 `unknown` 而用户只改了名字，旧代码还会把已有类别覆盖成 `unknown`。

**修复**（`app/item/[id].tsx` 的 `submit()`）：构造**真正的差量**，只发真正变化的字段；
颜色用无序集合比较（`sameStringSet`）以免服务端返回顺序不同就被误判为变化；
一个字段都没改时**关闭编辑器而不是发一次空 PATCH**。

**回归防护**：`mobile/scripts/verify/edit-payload-diff.mjs`（10 项）。
该测试已反验证：把旧写法改回去后它**确实会失败**，所以不是同义反复断言。

**附带修正**：`src/api/itemWrites.ts` 里那句「Editing a name alone does not」原本与客户端
实际行为相反，现已改为准确描述，并写明**调用方必须只发变化字段**的原因。

**设备脚手架的四处修复**（审计报告 B-3 / B-5 / B-12 等）：

1. `run-acceptance.sh` 的 s1/s4 原本 `tap_after_scrolling_to "保存"` —— 添加页的提交按钮
   文案是**「添加」**，「保存」只存在于详情页的编辑表单。因此按钮从未被按下、请求从未发出，
   6 次运行全部报「no new item appeared」。已改为「添加」。
2. s4 存在**空过即 PASS**：第一次上传失败时 `second_delta ≤ 0` 恒真，无条件 PASS。
   现已加硬性前置断言（首次上传必须真的新增一条），否则直接 FAIL。
3. `picker_take_photo` 在相册网格尚未渲染时就判定失败（只 dump 一次）。已改为重试等待。
4. `device-prep.sh` 的样张断言原本要求 MediaStore 行数**增加**，重跑时同名覆盖导致误报失败。
   已改为断言「四个样张都在 MediaStore 里」（幂等）。

**已知设计取舍（非缺陷）**：

1. **签名图片 URL「持有即可访问」**：1 小时内任何人拿到 URL 都能读图。这是上游既有设计
   （`app/utils/signed_urls.py`），本轮未改。
2. **无离线写入**：网络不可用时添加/编辑/归档/删除都会明确失败并保留输入，**不会**排队重试。
   这是第一轮就定下的范围（不做离线双向同步）。
3. **AI 关闭时的「识别失败」**：AI 关闭不会产生 `ai_error`（那是真正的 AI 失败才有）；
   关闭时服务端把物品标为 ready，界面不会谎称识别失败。
