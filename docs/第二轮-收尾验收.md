## 3. 本轮发现并修复的真实缺陷

### 3.1 🔴 脚手架与 App 互相踢下线：`external_id` 不一致（**本轮最重要的发现**）

**现象**：s1 连续失败，日志里 App 在提交前一刻落回登录页；后端日志同时出现
App 侧 `GET /items 401` 与脚手架侧 `GET /items 401`。

**排查过程**（每一步都是本机实测，不是推断）：

1. 设备侧 `SecureStore.xml` 在失败后变为**空 map**（`<map />`）→ App 主动清掉了凭证；
2. 后端 `uvicorn.log`：App 的衣柜查询在登录后**确实有 200**，随后变 401 → 不是一开始就坏；
3. 令牌本身：`exp - iat = 604800`（7 天），`curl` 复测同一令牌 150 秒后仍 200 → **不是过期**；
4. 库表直查：`harness@zhiyi-harness.com` 的 `external_id` 是 **`dev:harness@zhiyi-harness.com`**，
   而脚手架一直用**不带前缀**的邮箱当 `external_id`。

**根因**：`src/auth/AuthContext.tsx:213` 的 dev 登录用 `external_id = dev:<email>`；
`backend/app/services/user_service.py:73-86`（`sync_from_oidc`，docstring 写明是"认证提供方迁移"）
在 external_id 查不到、邮箱查得到时会**改写该行的 external_id**。访问令牌把 external_id 放在
`sub` 里，而 `get_current_user` 按 `sub` 查用户 —— 于是**每一次改写都让对方那一侧的令牌立刻失效**：
App 收到 401 → 判定凭证被拒 → 登出并清空 secure storage。

**修复**：脚手架（`run-acceptance.sh`、`device-prep.sh`）统一使用 `TEST_USER_EXTERNAL_ID="dev:$TEST_USER_EMAIL"`。

**实测对比**：

| 配置 | 结果 |
| --- | --- |
| 修复前（`external_id` = 纯邮箱） | App 登录后 **约 2 分钟内**被脚手架的一次 `/auth/sync` 踢下线，s1 失败 |
| 修复后（`external_id` = `dev:<email>`） | s1/s2/s5/s7/s8 全部通过；`external_id` 在整轮内保持不变 |

**为什么这件事必须写进报告**：审计报告 B-4/V2 把"重启后登录态是否恢复"判为"环境/时序相关，
不稳定"。本轮证明它**不是随机的**，而是由这个 `external_id` 改写决定的确定性行为 ——
修复后连续 3 次冷启动 3/3 恢复（§4.3）。审计员当时观察到"落到登录页"是同一条链路的另一种表现。

> **产品侧说明（本轮不改，只登记）**：这是后端既有的"按邮箱迁移认证提供方"能力，生产环境只有一个
> 提供方时不会触发。但它的副作用是"任何一次 external_id 改写都会静默作废已发令牌"，且
> `/auth/session` 之外没有任何续期机制。第三轮若要动认证，应把这条写进设计约束。

### 3.2 🟠 离线冷启动会落到登录页（登记，未改）

后端不可达时冷启动，App 会显示登录页。**这部分是源码里写明的取舍**
（`AuthContext.tsx:154-157`），且实测**不会清掉凭证**：

```
# 后端已停止时读取设备 secure storage
/data/data/com.zhiyi.wardrobe/shared_prefs/SecureStore.xml   →  645 字节，令牌仍在
```

后端恢复后重启 App 即恢复登录态（已实测）。本轮**未改**该行为：把它改成"离线也当作已登录"会
改变认证语义，超出收尾范围。已登记为第三轮可讨论项。

实测输出（2026-09-27 12:28，248 秒）：

```

==> 1. the backend is up and the app restores its session
  ok the session was restored from secure storage

  ok the user is told it failed (照片和填写的信息都已保留 / 上传失败)
  ok no false success (no 已添加)
  ok the typed name survived the failure
  ok the photo is still attached
  ok a retry control is offered

  ok the API is healthy again
  ok the retry succeeded from the preserved form (server items 0 -> 1)

```

截图：`offline-02-form-filled.png`（照片+名称）、`offline-03-after-submit.png`（失败面板，表单未丢）、
`offline-04-after-retry.png`。
失败面板的实际文案是 `照片和填写的信息都已保留，可以直接重试。`（`zh.addItem.inputKept`），
不是通用的 `上传失败` —— 两者都接受，但**报告里必须写实际出现的那一句**。

### 4.6 超时/不确定结果的如实说明

App 的删除确认对话框里 `确认删除` 之后没有做幂等承诺。本轮只验证了
"点击确认 → 服务端行消失 → 列表刷新"，**没有**验证"请求超时后的重试语义"，
因为 `DELETE /items/{id}` 本身没有幂等键，重试会得到 404。这一条保留在 §6 未验证项。
