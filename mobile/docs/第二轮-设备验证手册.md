# 第二轮 · 设备验证手册

知衣 Android 端第二轮验收的**可复现操作手册**。配套脚本在 `mobile/scripts/`，
所有命令都在本机实测过，输出见 §7。

- 目标：让「添加一件衣服 → 查看 → 修改 → 再次打开仍存在」这条链路可以被**机械地**验收，
  而不是靠人手点击后凭记忆判断。
- 环境：`zhiyi-test` AVD（Android 16 / API 36 / arm64-v8a），后端 `http://127.0.0.1:8000`，
  模拟器内访问宿主机用 `http://10.0.2.2:8000`。
- 工具链不在系统 PATH 里，一切通过 `android-env.sh` 解析。

---

## 0. 快速开始

```bash
cd wardrowbe

# 1) 让模拟器进入可跑场景的状态（幂等，可重复执行）
./mobile/scripts/device-prep.sh prepare

# 2) 脚手架自检（15 项，非零退出码表示失败）
./mobile/scripts/verify-device.sh

# 3) 跑验收场景
./mobile/scripts/run-acceptance.sh            # 全部（s1…s8）
./mobile/scripts/run-acceptance.sh s1 s2 s5   # 只跑指定场景
./mobile/scripts/run-acceptance.sh --list     # 每个场景做什么

# 4) 「失败保留输入 + 重试成功」需要后端不可达，所以是独立脚本
./mobile/scripts/verify-offline-retry.sh
```

**设备独占约定（重要，审计报告 B-6）**：三个脚手架脚本都会**独占一把设备锁**
（`/tmp/zhiyi-device-harness.lock`），同一台模拟器被两个会话同时驱动时点击会互相穿插
（实测：刚打开的表单被另一个会话滚动过并在里面打好了字），所以第二个会话会等待并打印
持锁者 pid。

**但锁只能约束脚手架，约束不了人**：跑脚手架期间**不要手动操作设备**，也不要让第二个
会话用 `adb` 直接驱动同一台 AVD —— 审计期间正是因为这样，同一份取证出现了两种互相矛盾的
失败原因。需要并行就另起一台 AVD（`-p` 指定不同 AVD 名）。

### 脚本清单

| 文件 | 作用 |
| --- | --- |
| `mobile/scripts/android-env.sh` | **被 source** 的公共片段：解析 SDK/JDK、设备锁、权限读写、UI dump（含重试）、ANR 处理 |
| `mobile/scripts/device-prep.sh` | 设备准备与交互原语：`prepare` / `install` / `push-sample-photos` / `grant-permissions` / `deny-permissions` / `permission-state` / `shot` / `dump` / `reset` / `tap` / `tap-text` / `type` / `hide-keyboard` / `swipe` / `clear-test-user` |
| `mobile/scripts/verify-device.sh` | 脚手架自检，证明「设备 + App + 后端 + 抓取能力」四件事都成立 |
| `mobile/scripts/run-acceptance.sh` | 机械执行验收场景 **s1…s8**（`--list` 查看每个场景；每个场景自带前置，不再隐式依赖"先跑过 s1"） |
| `mobile/scripts/verify-offline-retry.sh` | 「上传失败保留输入 + 后端恢复后重试成功」。它只停 API、保留 PostgreSQL，并用 `trap … EXIT` 保证失败也不会把后端留在停止状态 |
| `mobile/scripts/ui-dump-report.py` | 解析 `uiautomator dump`：识别当前是哪个页面、按文案解析出可点击节点的坐标 |

产物（截图 + UI dump）写到 `mobile/docs/device-shots/`。

## 1. 环境准备

```bash
export ANDROID_HOME=/tmp/zhiyi-android/sdk          # 或直接 source android-env.sh
ADB=$ANDROID_HOME/platform-tools/adb

## 2. 相册照片的准备与索引

**这是最容易踩空的一步**：只把文件 `adb push` 进设备，相册和系统相册选择器**都看不到它**。

```bash
# 生成 + 推送 + 让 MediaStore 索引（幂等）
./mobile/scripts/device-prep.sh push-sample-photos
```

生成 4 张照片到 `mobile/docs/device-shots/sample-photos/`：

| 文件 | 尺寸 | 用途 |
| --- | --- | --- |
| `sample-A.jpg` | 1600×1200 | 纯色底 + 大号字母 A，用于观察客户端是否真的压缩 |
| `sample-B.jpg` | 1600×1200 | 同上，B |
| `sample-C.jpg` | 1600×1200 | 同上，C |
| `sample-D-rotated.jpg` | 1200×1600 | **带 EXIF Orientation=6**，用于验证方向是否被正确处理 |

实测的索引方式（**唯一有效的那条**）：

```bash
$ADB push sample-A.jpg /sdcard/Pictures/zhiyi/
$ADB shell am broadcast \
  -a android.intent.action.MEDIA_SCANNER_SCAN_FILE \
  -d file:///sdcard/Pictures/zhiyi/sample-A.jpg
```

验证：

```bash
$ADB shell content query --uri content://media/external/images/media \
  --projection _id:_display_name:_size

# Row: 0 _id=19, _display_name=sample-A.jpg, _size=36477
# Row: 1 _id=20, _display_name=sample-B.jpg, _size=36159
# Row: 2 _id=21, _display_name=sample-C.jpg, _size=35934
# Row: 3 _id=22, _display_name=sample-D-rotated.jpg, _size=35779
```

实测结论：
- `adb push` 之后**没有广播**时，`content query` 返回 `No result found.` —— 文件在磁盘上，但
  MediaStore 里没有行，相册看不到。
- `MEDIA_SCANNER_SCAN_FILE` 广播在这台 API 36 上是**有效**的，一次广播插入一行。
- 该脚本断言的是「每张样片都能在 MediaStore 里查到」，**不是**「行数必须增加」：
  重复执行会覆盖同名文件，行数合法地不变，按增量断言会让第二次运行误报失败。

## 3. 权限控制

```bash
./mobile/scripts/device-prep.sh permission-state        # 当前声明/授权状态
./mobile/scripts/device-prep.sh grant-permissions       # 授予 CAMERA + 照片权限
./mobile/scripts/device-prep.sh deny-permissions soft   # 拒绝：App 仍可再次申请
./mobile/scripts/device-prep.sh deny-permissions hard   # 永久拒绝：canAskAgain=false
```

### 权限名（实测）

| 权限 | 说明 |
| --- | --- |
| `android.permission.CAMERA` | expo-image-picker 模块**无条件声明**；相机场景的前提 |
| `READ_MEDIA_IMAGES` / `READ_MEDIA_VISUAL_USER_SELECTED` | 仅 API 33+；**照片选择流程并不需要它** |
| `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` | 声明时带 `maxSdkVersion=32`，在 API 36 上**根本不出现** |

照片选择之所以不需要照片权限：Android 13 起系统 PhotoPicker 对用户选中的那一个 URI
下发读授权。所以「相册打不开」**不可能**是缺 `READ_MEDIA_IMAGES` 导致的，别往这个方向查。

### 拒绝的两种程度

```bash
# soft：撤权但 App 仍可再次申请 → 系统弹窗会再次出现
$ADB shell pm revoke com.zhiyi.wardrobe android.permission.CAMERA

# hard：额外打上 USER_FIXED → App 拿到 canAskAgain=false，系统不再弹窗
$ADB shell pm set-permission-flags com.zhiyi.wardrobe android.permission.CAMERA user-fixed

# 恢复成「可再次申请」
$ADB shell pm clear-permission-flags com.zhiyi.wardrobe android.permission.CAMERA user-fixed
```

Expo 的 `canAskAgain` 来源：`expo-modules-core` 的 `PermissionsService`，在被拒绝且
`shouldShowRequestPermissionRationale` 为 false 时把该权限记为 blocked，并持久化到
SharedPreferences。所以 `hard` 模式正好复现「用户点了两次不允许」的结果。

读回当前状态：

```bash
$ADB shell dumpsys package com.zhiyi.wardrobe | sed -n '/runtime permissions:/,/^$/p'
# 或
./mobile/scripts/device-prep.sh permission-state
```

> `appops set --uid <pkg> CAMERA ignore` 也能拦住相机访问，但**不会**改变 Expo 看到的
> `granted` 状态 → App 仍以为有权限，只是调用失败。要验证「权限被拒绝」的 UI 分支，
> 用 `pm revoke`，不要用 appops。

## 4. 各验收场景

`run-acceptance.sh` 尽量机械化，但有几处**物理上无法脚本化**，一律标成 `MANUAL`，
不假装通过。

### 场景 1 —— 从相册添加一件衣服，刷新与重启后仍在

**可完全脚本化**：`./mobile/scripts/run-acceptance.sh s1`

关键点是系统相册选择器**是一个普通 Activity**，它的元素带 `content-desc` 和 `bounds`，
所以可以脚本化点击：

```bash
# App 内：点「添加单品」→「从相册选择」
./mobile/scripts/device-prep.sh tap-text "添加单品"
./mobile/scripts/device-prep.sh tap-text "从相册选择"
sleep 6
$ADB shell dumpsys activity activities | grep -m1 topResumedActivity
# topResumedActivity=ActivityRecord{... com.google.android.providers.media.module/...PhotoPickerActivity t17}

# 选择器里的照片是「clickable=true 且 content-desc 形如 Photo taken on ...」的 FrameLayout
# run-acceptance.sh 的 picker_take_photo 就是按这个规则取 bounds 再 tap
```

脚本随后断言（顺序即失败定位顺序）：

1. 选择器确实被拉起（否则报 FAIL，而不是继续点一片空白）
2. 选中后回到表单，且**不再是**「还没有选择照片」→ 照片已挂上
3. 填入名称、保存后，**后端**上该用户的件数增加（`GET /items` 的 `total`）
4. 后端存储的名字与输入的名字一致
5. `force-stop` → 重新启动后，该名称**仍然可见**

第 3 步用后端而不是纯截图断言，因为截图无法区分「上传失败」和「上传成功但列表是旧的」。

手工复现（若脚本失败要定位）：

```bash
./mobile/scripts/device-prep.sh shot before-add
./mobile/scripts/device-prep.sh tap-text "添加单品"
./mobile/scripts/device-prep.sh tap-text "从相册选择"
sleep 6
./mobile/scripts/device-prep.sh dump picker        # 看选择器里的坐标
./mobile/scripts/device-prep.sh tap 177 1586       # 换成 dump 出来的第一个照片块中心
./mobile/scripts/device-prep.sh shot after-pick
```

### 场景 2 —— 修改名称或分类后，列表/详情/筛选一致

**可脚本化，但依赖详情页的编辑入口**：`run-acceptance.sh s6` 只覆盖了归档路径。
改名的机械步骤：

```bash
./mobile/scripts/run-acceptance.sh s1          # 先保证有一件
./mobile/scripts/device-prep.sh tap-text "衣橱"  # 回衣橱
# 打开第一件：它的坐标从当前 dump 里取（见 run-acceptance.sh 的 s6 取 tile 的方法）
./mobile/scripts/device-prep.sh dump wardrobe
./mobile/scripts/device-prep.sh tap <x> <y>    # 第一件单品的中心
sleep 4
./mobile/scripts/device-prep.sh dump detail
./mobile/scripts/device-prep.sh tap-text "编辑"
# …改成新名字后保存
```

一致性判定（三者必须一致）：详情页显示的名字 = 列表里该件显示的名字 = 改动后重新拉取
`GET /items?search=<新名字>` 能命中。

### 场景 3 —— 拒绝权限 / 取消选择 / 上传失败，界面可恢复且不产生假成功

`./mobile/scripts/run-acceptance.sh s3`，三段：

| 子场景 | 是否脚本化 | 命令 |
| --- | --- | --- |
| 相机被永久拒绝 | ✅ | `deny-permissions hard` → 点「拍照」→ 断言仍停在表单、可重试、无崩溃 |
| 取消选择 | ✅ | 拉起选择器 → 点 `Cancel` → 断言回到初始表单且无附件 |
| 上传失败 | ❌ **MANUAL** | 需要把 App 指向不可达后端，只能重新打包 |

上传失败的机械前提（本轮未做，故标 MANUAL）：

```bash
# 用一个指向死端口的 bundle 重新打包，再跑
API_URL=http://10.0.2.2:9 ./mobile/scripts/build-android.sh
./mobile/scripts/device-prep.sh install
# 之后：添加 → 保存 → 应显示可读错误、保留已填内容、提供重试
```

### 场景 4 —— 同一次上传重试不产生重复记录

`./mobile/scripts/run-acceptance.sh s4`

做法：同一张照片走两次添加流程，**第二次故意连点两次保存**（模拟用户不耐烦的重试），
然后断言后端件数**没有增加**。

后端有两道防线（读 `backend/app/api/items.py` 与 `item_service`）：

- `POST /items`：`compute_phash` + `find_duplicate_by_hash` → 重复图片直接 **409**
- `POST /items/bulk`：额外的 `upload_keys` 幂等键 + DB 唯一约束

> 注意：**单件接口 `POST /items` 没有 `upload_keys` 参数**，幂等键只在 `/bulk` 上存在。
> 所以「同一次上传重试不重复」在单件路径上靠的是感知哈希查重，不是幂等键。

### 场景 5 —— AI 关闭或失败时仍能手动录入

本轮后端 `ai.vision=false`（`GET /api/v1/capabilities` 实测），所以**手动录入就是当前
唯一路径**，也正好是 s1 覆盖的内容。自检会显式报告这一点：

```
PASS ai-vision-off   AI vision disabled — the manual-entry path (acceptance scenario 5) is the live path
```

### 场景 6 —— 归档或删除后列表及时更新

`./mobile/scripts/run-acceptance.sh s6`

先记录后端件数 → 打开第一件详情 → 点归档/删除（+ 可能的确认）→ 断言后端件数下降且
列表已刷新。若详情页找不到归档控件，脚本**不猜**，直接标 `MANUAL`。

## 6. 已知坑（都是实测撞过的）

1. **`adb push` 不会让相册看到照片。** 必须补 `MEDIA_SCANNER_SCAN_FILE` 广播，
   否则相册与系统选择器都是空的，场景 1 从第一步就走不通。

2. **无 GPU 的模拟器会弹 SystemUI ANR 弹窗，吞掉所有输入。**
   本 AVD 是 `hw.gpu.enabled=no`，SystemUI 会周期性地「无响应」，弹出
   `System UI isn't responding` 并抢占焦点。此时 `input tap` 全部进了弹窗，App 看起来像卡死。
   实测：弹窗在时点击 App 完全无反应；设置 `settings put global hide_error_dialogs 1`
   并清掉已弹出的窗口后才恢复。`device-prep.sh prepare` 已包含这一步。

3. **`uiautomator dump` 大约 30% 概率返回空。**
   实测 20 次连续调用失败 6 次，且不是「坏 XML」而是**完全没有输出**。
   单次调用当作结论会让每次 `tap-text` 都偶发失败 → `ui_dump_xml` 内置 5 次重试，
   重试后实测 15/15 成功。

4. **`pm grant` 对没声明的权限会静默成功（exit 0）且什么都不做。**
   所以必须先用 `dumpsys package` 确认该权限在 `requested permissions` 里再授权，
   否则会得到「命令成功但状态没变」的假象。`app_declares_permission` 就是干这个的。

5. **`... | grep -q` 在 `set -o pipefail` 下会在匹配成功时报 141。**
   `grep -q` 一命中就退出，上游进程收到 SIGPIPE，管道整体返回 141 ——
   于是一次**成功**的匹配被当成失败。这个坑曾静默地让所有权限检测失效。
   改用读完全部输入的 `grep -c`（`has_match` 函数）。

6. **bounds 字符串里的 `][` 分割符不能直接过滤数字。**
   `[76,1238][1004,1358]` 若只保留数字，`1238` 和 `1004` 会粘成 `12381004`，`y2` 变空，
   点击静默落到空处。必须先把 `][` 换成 `,`，再切分（`tap_bounds` 已处理）。
   顺带：BSD `sed` 不接受 `s/][/,/`，要用 bash 替换。

7. **软键盘会挡住下半屏的输入框。**
   点完邮箱框输入后，直接点下面的「显示名称」框会点到键盘上，文字进错字段。
   正确顺序：`tap 字段 → type → hide-keyboard → tap 下一个字段`。
   `hide-keyboard` 用 ESCAPE（`input keyevent 111`）而不是 BACK，避免触发返回导航。

   而且在**添加单品页这个长表单上尤其致命**：名称框初始位于 y≈1790，正好在键盘区域内，
   点击落在键盘上、字段根本不获得焦点，于是 `input text` 把字打进空白。
   实测直到最后一步（后端上的名字与输入不符）才失败。
   所以 `type_into_scrolled_field` 必须先 `hide-keyboard`，点完再**验证字段真的拿到焦点**，
   输入后再**回读确认**，三者缺一都会把失败掩盖成别的问题。


8. **`adb shell input text` 会静默丢字（本轮最坑的一个）。**
   它注入按键事件的速度快过 React Native `TextInput` 的处理速度，超出的字会**被默默丢弃**，
   不报错、不返回非零。实测：
   - 往名称框输入 `IMMEDIATE` → 框里只有 `IMMED`
   - 往输入框输入 21 字符的邮箱 → 框里**什么都没有**
   - 成功率与字符串长度、当时负载相关，所以会表现为「偶发」

   危害在于**失败位置错位**：文字没进去，脚本直到最后断言「后端上的名字与输入不符」
   才报错，看上去像上传或命名功能有问题，实际是输入根本没发生。
   处理：`device-prep.sh type` 现在会**回读校验**（先整串发，读回不对就清空后逐字符发），
   并把结果如实报出来，而不是假设成功。

   另外两个必须处理的转义（都已实测）：空格要写成 `%s`；字面量 `%` 要写成 `%25`。

   更绝对的约束：**`input text` 完全无法输入非 ASCII 字符。**
   发中文会直接抛 `NullPointerException`（`InputShellCommand.sendText`），
   一个字也进不去，且不留下任何部分结果。实测发 `衬衫` 后字段仍是空的。

   这条曾经让我自己误判：脚本用中文测试名（`脚手架衬衫-HHMMSS`），
   字段一直为空，而断言是最后才跑的 —— 表现为「上传功能不工作」，
   实际是输入手段本身不支持中文。现在 `type` 会**主动拒绝非 ASCII 并说明原因**，
   脚本里的测试名也改成 ASCII。中文录入需要走屏幕输入法或剪贴板粘贴，不能这样脚本化。


9. **`type` 必须先把字段清空，否则结果依赖上一次状态。**
   追加式输入会让「第二次输入」得到 `FIRSTSECOND`，让失败看起来像别的问题。
   现在 `type` 是**设定**而非追加：实测连续 `type FIRST` → `type SECOND` 后字段为 `SECOND`。

10. **清空长字段要用一次设备端批量按键，不要 100 次 adb 往返。**
   `adb shell input keyevent KEYCODE_DEL KEYCODE_DEL …`（一次传 100 个）实测耗时 ~0.5s；
   逐个往返要 ~6s，会成为每个场景最慢的一步。

11. **子 shell 里赋值的变量活不到外面。**
   `count="$(api_item_count)"` 这种用法下，函数内部对 `TOKEN` 的赋值随着子 shell 一起消失，
   导致每次调用都重新登录 —— 慢且会偶发 `curl: (22) … 401`。令牌要落到**文件**里缓存
   （`run-acceptance.sh` 的 `TOKEN_CACHE`），并在 401 时清掉重登一次。

12. **`run-acceptance.sh` 调用 `device-prep.sh`：设备锁必须是可重入的。**
   否则外层已持锁，内层再申请就会**等自己**，直接死锁。
   实测过一次：`run-acceptance.sh` 卡在 `device-prep.sh deny-permissions` 里 6 分钟不动。
   而且 `exec` 会重置 trap —— 锁的释放 trap 必须由 exec 之后的子进程安装，
   否则锁目录永远不会被删。丢失的锁现在靠 pid 存活检测自动回收。

14. **`uiautomator dump` 的收尾行拼写是 `UI hierchary dumped to:`**（原文如此，少一个 `a`）。
   解析时要整行丢掉，否则 XML 尾部带垃圾导致解析失败。

15. **XML 里的 `text` 与 `content-desc` 两处都可能承载文案。**
   按钮常常是「空 text + 有 content-desc」（例如 `desc='从相册选择'`），
   只查 `text` 会找不到它。

16. **不要用调试字段或内部状态枚举做断言。**
   `ui-dump-report.py` 只匹配 App 自己渲染的中文文案；
   匹配不到就报 FAIL，从而避免「把系统弹窗或启动器当成 App」的假通过。
   这一条也是上面「拒绝相机」场景能可靠区分 添加单品页 / 登录页 / 启动器 的原因。

17. **不要用固定 `sleep` 等 App 启动。**
   无 GPU 的模拟器上，release 包的冷启动到**第一帧渲染完成**实测需要 **~20s**
   （实测 21s；同一台设备上另一轮只用了 3s，取决于当时负载）。
   原来写死在 `am start` 后 `sleep 8`，结果 dump 到的是一个**还没渲染的空白 React root**，
   自检报「App 在前台但没有任何已知文案」—— 看上去像 App 坏了，实际只是等得太早。
   现在统一用 `wait_for_ui_ready [秒]`（轮询到 dump 里出现第一个非空 text 为止），
   并在自检里把真实耗时打出来（`==> UI painted after Ns`）。

   同类问题还有两处：登录前固定 `sleep 8`、重启后固定 `sleep 10`，都已改成同一个等待函数。
   规则：**能用「等到某个可观测条件成立」就不要用固定延时。**

18. **测试账号的 `external_id` 必须与 App 的 dev 登录一致：`dev:<email>`。**
   这一条是收尾阶段花了两个多小时才定位的**根因**，也解释了此前所有"登录态不稳定"的结论。

   `src/auth/AuthContext.tsx:213` 的 dev 登录用 `external_id = dev:<email>`；
   而后端 `UserService.sync_from_oidc`（`app/services/user_service.py:73-86`，docstring 写明是
   "认证提供方迁移"）在 external_id 查不到、邮箱查得到时，会**把该行的 external_id 改写成刚到达的值**。
   访问令牌把 external_id 放在 `sub`，`get_current_user` 按 `sub` 查用户 ——
   于是**脚手架每调一次 `/auth/sync`，都可能让 App 手上那张令牌立刻变成 401**；
   App 判定"凭证被拒"→ 自我登出并清空 secure storage（`SecureStore.xml` 变回空 map）。

   表现极具迷惑性：App 登录后**确实**有几分钟是好的（衣柜查询 200），然后突然 401；
   脚手架自己也会周期性地拿到 401（反向同理）。两边看起来都"随机失败"。

   实测：修复前 App 登录后约 2 分钟内被踢下线；改成 `TEST_USER_EXTERNAL_ID="dev:$TEST_USER_EMAIL"`
   之后，`external_id` 在整轮里保持不变，s1/s2/s5/s7/s8 全部通过。

19. **`GET /items?is_archived=true` 的意思是"只取已归档"，不是"包含已归档"。**
   脚手架的 `api_item_ids()` 曾只查这一侧，于是 `api_delete_all` **从来没有删掉过任何普通衣物**，
   却让调用方以为衣柜已经清空 —— 随后新上传的样张被 pHash 判为重复、返回 409，
   场景便报"没有新增"，看上去像产品缺陷。现在同时查 `false` 与 `true`。

20. **"第一个可点击节点"会命中筛选芯片，而不是衣物卡片。**
    衣柜页在卡片上方有一排类型芯片（`所有类型`、`待分类 (1)`…），宽度约 200px、顶边 y=545；
    衣物卡片宽约 478px、顶边 y=661。只按 y 区间选点会点到芯片，于是"点开详情"其实什么也没打开。
    现在优先按卡片 `content-desc`（就是衣物名称）精确点击，位置兜底规则同时要求
    `y > 640` 且宽度 `> 300`。

21. **用 API 改过数据之后，先冷启动 App 再点。**
    App 是按"页面重新获得焦点"（以及 30s 空闲轮询）刷新衣柜的，脚本改完数据立刻点卡片，
    可能点到一个**已经被删掉的行**，详情页返回 404 并渲染 `未找到该单品` ——
    看起来像产品 bug，实际是测试在读陈旧列表。见 `restart_app_fresh()`。

22. **判断"表单是否打开"不要等屏幕外的文案。**
    编辑表单底部有 `都可以稍后修改`，但它在折叠线以下、dump 里根本没有，
    于是"等它出现"会把一个明明已经打开的表单判成"没打开"。
    改用只在编辑态出现的 `类别` 标签（只读详情页是 `类型`），两者可区分。

23. **要在折叠线以下的按钮上点击，必须先滚动。**
    添加页的 `添加`、详情页的 `归档`/`删除` 都在屏幕外。裸 `tap-text` 找不到节点就**静默什么都不做**
    （驱动脚本第一次写时就是这样，然后去怪产品"没有失败提示"）。
    统一用 `tap_after_scrolling_to`（`run-acceptance.sh`）或 `verify-offline-retry.sh` 里的
    `tap_after_scroll`。

## 10. 本轮的卡点：设备被并发占用

场景 1/4 的端到端断言没跑完，原因是一个**环境问题，不是脚本逻辑问题**：
这台模拟器同时被另一个会话驱动。实测到的现象：

- 我的运行中途，App 被外部 `am force-stop` 了十几次（`logcat` 里能看到
  `Force stopping com.zhiyi.wardrobe ... from pid <外部 pid>`）
- 同一台设备上出现了别的会话造出来的 UI 状态：表单被滚动过、输入框里出现 `BlueShirt`、
  单品详情里出现 `BlobFixVerified`/`大衣` 这类我没写过的数据
- 设备前台会在我的步骤之间变成 `com.google.android.providers.media.module`、
  `com.android.camera2`、甚至启动器（因为另一个会话把 App 强制停止了）

已做的防护（都已实测）：

1. **设备锁**（`/tmp/zhiyi-device-harness.lock`）：可重入、pid 存活检测、陈锁自动回收。
   已实测：独立进程会被正确阻塞；嵌套调用不会死锁；被杀死的运行不会永久卡住后续运行。
2. **外来 Activity 恢复**：`goto_wardrobe` / `open_add_screen` 会先判断前台是不是自己的 App，
   不是就先 BACK、必要时强制停止 picker / 相机，再重新拉起 App。

但仍有一个残留局限：**锁只能约束使用这套脚本的运行方**。另一个会话若不经由这些脚本
（直接 `adb shell am force-stop`），锁拦不住它 —— 实测就是这样丢的会话。
因此结论是：

> 要拿到场景 1/4 的完整 PASS，需要在**独占**模拟器的时间窗口里重跑：
> ```bash
> ./mobile/scripts/device-prep.sh prepare
> ./mobile/scripts/run-acceptance.sh s1 s4
> ```
> 脚本本身已就绪；缺的是一段没有第二个驱动者的时间。

### 顺带查到的一个真问题（已修）

测试账号最初用 `harness@zhiyi-dev.test`，结果是 **`.test` 是保留 TLD**：
`POST /auth/sync` 收下它，但 `GET /auth/session` 把 `email` 校验为 `EmailStr` 并返回 **422**，
客户端把 422 当作「凭证不可用」从而强制登出。实测：

```
harness@zhiyi-dev.test      /auth/sync 200, /auth/session 422  -> App 中途被踢回登录页
harness@zhiyi-harness.com   /auth/sync 200, /auth/session 200  -> 正常
```

这正是 `mobile/README.md` §5 已经写明的坑（“不要用 `.local` 结尾的邮箱”），
本轮在设备上又确认了一遍，并已把测试账号改成真实 TLD，同时加了启动断言：
账号过不了 `/auth/session` 就直接报错退出，而不是让它变成中途登出。
