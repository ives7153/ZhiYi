## 0. 结论摘要（先看这四条）

1. **应该重新编码，但理由不是"picker 会导致二次旋转"。** 我逐条复现了四条路径（`quality:1` 原样直传 / picker 压缩 / manipulator / `allowsEditing` 裁剪），它们的后端落盘结果**全部正确且 pHash 完全相同**（§3.2）——因为 picker 的 `copyExifData` 把 `TAG_ORIENTATION` 排除了（`ImagePickerUtils.kt:217`）。真正的理由是：(a) 现正确性依赖三个 exporter 的**隐式互补**，改一下 `quality` 就会切换路径；(b) 原图直传会撞后端 20MB / 50MP 硬限制；(c) manipulator 的输出 EXIF 干净（该模块全目录零 `ExifInterface`），自洽且不依赖任何隐式契约。
2. **picker 返回的 uri 一定是 `file://`，不是 `content://`。** 出处：`MediaHandler.kt:69` 的 `Uri.fromFile(outputFile).toString()`。所以**不需要**做 `content://` → `file://` 的拷贝转换；RN 的 `RequestBodyUtil.getFileInputStream` 两种都支持（`RequestBodyUtil.kt:75`）。
3. **⚠️ 本节结论只适用于 React Native **原生** 网络栈**（即设置 `EXPO_PUBLIC_USE_RN_FETCH=1` 时）。本仓库**未设**该变量，因此实际走的是 **Expo 自己的 `fetch`**，那里 `{uri}` 分片会抛异常——见文末「与 Expo fetch 的关系」一节。
   `{ uri, name, type }` 在 RN 原生网络栈下正确且必需，且 `type` **不能省**——省了 Native 层直接报 `Binary FormData part needs a content-type header`（`NetworkingModule.kt:972`）。同时**不要手写 `Content-Type`**（原因见 §4.2）。
4. **`fetch` 不暴露上传进度**（whatwg-fetch 只用 `xhr.onload`，没有 `xhr.upload`）；但 RN 的 XHR **支持**上传进度，`xhr.upload.onprogress` 可用（`XMLHttpRequest.js:576-577`）。

`PermissionResponse` 来自 `expo-modules-core`，字段为 `granted: boolean`、`status: 'granted'|'denied'|'undetermined'`、`canAskAgain: boolean`、`expires`。

**如何区分 denied / 永久拒绝 / 未决定**（**我的推断**，依据上述字段语义）：
- 未决定：`status === 'undetermined'`
- 普通拒绝（还能再弹窗）：`granted === false && canAskAgain === true`
- 永久拒绝（必须去设置页）：`granted === false && canAskAgain === false`

⚠️ **Android 上的重要陷阱（我读到的原文）**：`ImagePickerModule.kt:258-266`

```kotlin
private fun getMediaLibraryPermissions(writeOnly: Boolean): Array<String> =
  if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    emptyArray<String>()          // ← API 33+ 需要申请的权限是「空数组」
  } else {
    listOfNotNull(
      Manifest.permission.WRITE_EXTERNAL_STORAGE,
      Manifest.permission.READ_EXTERNAL_STORAGE.takeIf { !writeOnly }
    ).toTypedArray()
  }
```

**结论**：在 Android 13+（API 33+）上 `requestMediaLibraryPermissionsAsync()` 申请的是一个**空权限列表**。系统相册选择器（Photo Picker）本身不需要运行时权限。
**我的推断**：因此在 API 33+ 上，**不应该**把 `granted === false` 当作"阻止选图"的理由——应以 `launchImageLibraryAsync` 的实际结果为准。本仓库 `photoPicker.ts` 的 `pickFromLibrary` 只把 `canAskAgain === false` 当硬性阻断，方向是对的。
同时注意：**Android 上不存在 `accessPrivileges` 的真实读取**——`ImagePicker.types.d.ts:13` 说明 `'limited'` 仅 Android API 34+ 与 iOS 14+ 有效。

## 3. 方向问题的可复现实验（本报告的核心证据）

### 3.1 实验方法

造一张**像素是 1600×1200 横图、但 EXIF Orientation=6（顺时针 90°）**的 JPEG——这正是手机竖拍照片的存储方式。然后把它分别按三条客户端路径处理后，喂进**真实的后端 `ImageService.process_and_store`**，读实际落盘文件的几何与 EXIF。

构造脚本（`/tmp/exiftest/make_src.py` 核心）：

```python
W, H = 1600, 1200
exif[0x0112] = 6          # Orientation = 6 (Rotate 90 CW)
img.save("src_orientation6.jpg", quality=95, exif=exif)
```

输出：`stored size (raw pixels): (1600, 1200)`，`EXIF Orientation read back: 6`。

### 3.2 实验结果

驱动脚本：直接 `sys.path.insert` 后端并 `asyncio.run(svc.process_and_store(...))`。

```

------------------------------------------------------------------------------------------------

**四条路径的 pHash 完全一致（`83fe03fc02fcfc01`），四条路径产出的图在视觉上完全相同。**

### 3.3 直接回答「是否必须重新编码」

> **问题**：照片是否必须在客户端重新编码，才能避免后端把图转两次？

**答案：不是"必须"，但强烈建议，且理由是双重的。**

**证据层面**：上面四条路径**没有任何一条**会产生"转两次"。原假设中的危险组合——"像素已转正 + 仍带 Orientation 标签"——在 SDK 57 的代码里**根本无法通过 picker 产生**，因为：
- `quality: 1`（RawImageExporter）→ 像素**未**转正，标签**保留** → 后端转一次 → ✅ 正确
- `0 < quality < 1`（CompressionImageExporter）→ 像素**已**转正，标签**被排除** → 后端再转是 no-op → ✅ 正确
- `allowsEditing: true`（Cropper）→ 像素**已**转正，`copyExifData` 同样排除 Orientation → ✅ 正确

三者互补，恰好不会撞车。

**我另外构造了这个危险组合来确认它确实是错的**（人工把"已转正的像素 + Orientation=6"拼在一起送进同一后端）：

```
D_oriented_pixels+BAD_tag          submitted=(1200,1600) OriTag=6 → stored=(1600,1200)  ← 被侧翻了
```

**我的推断**：既然这个组合有害，那么**任何会在客户端改动像素、却又不清理 EXIF 的第三方步骤**都会踩到它。所以真正的风险不在于 picker，而在于"未来某次改动"。

**因此结论是：仍然应该在客户端统一过一遍 `expo-image-manipulator`**，理由不是"避免二次旋转"（那个具体说法在当前 SDK 版本下不成立），而是：
1. **让方向处理不依赖 `quality` 的取值**。当前正确性建立在"三个 exporter 恰好互补"上；这是隐式契约，一旦有人把 `quality` 从 `1` 改掉、或开启 `allowsEditing`，路径就切换了。重编码把它压成一条路径。
2. **满足后端的两条硬限制**：`image_service.py:204` 拒绝 > 20MB；`image_service.py:88` 按 `max_image_megapixels`（`.env` 默认 50MP）拒绝超大图。原图直传在 48MP+ 手机上会直接 400。
3. **manipulator 输出的 EXIF 是干净的**——`expo-image-manipulator/android` 全目录 `grep -r "ExifInterface\|Exif"` **零命中**（我实测过），且它加载图片也走 Glide（因此像素已转正）。像素转正 + 无 EXIF = 自洽。

> ⚠️ **与 master 结论的唯一冲突**：master 判断"picker 的 `CompressionImageExporter` 会抄回一个已被应用过的 orientation 标签"。**这一条在 SDK 57.0.20 上不成立**，`TAG_ORIENTATION` 在 `omittableTags` 中（`ImagePickerUtils.kt:212-218`）。但**"应该过一遍 manipulator"这个最终行动建议不变**，理由如上三条。

## 4. React Native 0.86 FormData 上传

**我读到的原文**（`react-native/Libraries/Network/FormData.js:13`）：

}
```

**结论（限定于 RN 原生网络栈）**：`{ uri, name, type }` 是这条路径下唯一正确的写法。`name` 和 `type` 在类型上是 optional，但见下条——`type` 实际必填。

> ⚠️ **范围警告**：以上读的是 `NetworkingModule.kt`（RN 原生）。本仓库**不走这条路**，见文末「与 Expo fetch 的关系」。若你在别处看到「Blob 不支持」的结论，请注意它同样只对原生网络栈成立。

> **`type` 不能省（我读到的原文）**：`NetworkingModule.kt:965-978`。如果一个 part 带 `uri` 但没有 `content-type`，Native 层直接报错返回：
> ```
> "Binary FormData part needs a content-type header."
> ```
> 所以 **`type` 是事实上的必填项**，`name` 也几乎必填（否则服务端拿不到 filename）。

### 4.2 为什么**必须不要**手写 `Content-Type`

**我读到的原文**：
- `FormData.js` 只产出**每个 part 自己的** headers（`content-disposition` / `content-type`），**不产出**整个请求的 `Content-Type`。
- `NetworkingModule.kt:578-580`：
  ```kotlin
  data.hasKey(REQUEST_BODY_KEY_FORMDATA) -> {
    if (contentType == null) {
      contentType = "multipart/form-data"     // 没有就补上
    }
  ```
- `NetworkingModule.kt:949-954`：part 级别的 `content-type` 被**从 headers 里移除**，改为显式传给 `MultipartBody.Builder`。
- OkHttp `MultipartBody.kt:38`：`private val contentType: MediaType = "$type; boundary=$boundary"`——**boundary 由 OkHttp 生成**。

**结论**：如果你手写 `Content-Type: multipart/form-data`，OkHttp 的 `BridgeInterceptor.kt:43-46` 会用 body 自己的 contentType（含 boundary）**覆盖**你写的值：

```kotlin
val contentType = body.contentType()
if (contentType != null) {
  requestBuilder.header("Content-Type", contentType.toString())
}
```

**我的推断**：即使写错了也不会真的坏，但**手写的那个没有 boundary**，一旦 OkHttp 的覆盖行为因为版本变化而改变，服务端就会解析失败。**正确做法就是不设置**——本仓库 `mobile/src/api/client.ts` 中 `requestMultipart` 的 `headers` 只有 `Accept` 与 `Authorization`，并在 `Deliberately no Content-Type` 注释处明确说明了这一点，写法是对的。

> 注：`FormData.js:36-38` 的 `encodeFilename` 会把 `/` 替换成 `_` 再 `encodeURIComponent`。所以 `name` 里带路径会被改写——用普通文件名即可。

### 4.3 `uri` 是否必须带 `file://`

**我读到的原文**（`RequestBodyUtil.kt:55-80`）：

```kotlin
fun getFileInputStream(context: Context, fileContentUriStr: String): InputStream? {
  val fileContentUri = Uri.parse(fileContentUriStr)
  if (fileContentUri.scheme?.startsWith("http") == true) {
    return getDownloadFileInputStream(context, fileContentUri)   // http/https 会先下载
  }
  if (fileContentUriStr.startsWith("data:")) { ... }             // data: URI 走 base64 解码
  return context.contentResolver.openInputStream(fileContentUri)  // 其余交给 ContentResolver
}
```

**结论**：
- **`file://` 不需要**你手动加——`contentResolver.openInputStream()` 能直接处理 `file://` 与 `content://` 两种 scheme。
- picker 返回的本来就是 `file://`（§2.6 已证），所以**直接喂进去即可**。
- 还有两个额外能力：`http(s)://` 会自动下载到临时文件，`data:` 会 base64 解码。**本项目都不需要**。

### 4.4 `content://` 与 picker 的返回值

**我读到的原文**：
- picker 内部**确实**会拿到 `content://`——`ImageLibraryContract.kt:22-23` 的类注释："receiving a `content://` Uri for each piece of content"；相机路径的临时文件用 FileProvider 转成 `content://`（`ImagePickerUtils.kt:67-80` 的 `getContentUri`/`toContentUri`，`ImagePickerModule.kt:76`）。
- **但返回给 JS 的永远是 `file://`**——因为所有 source 都会被 exporter 复制/重编码到 cache 目录，然后 `MediaHandler.kt:69` 用 `Uri.fromFile(outputFile).toString()` 输出。

**结论：不需要做 `content://` → `file://` 的转换。** 唯一的例外是 `readExtras` 里 `mediaType == null` 的分支（`MediaHandler.kt:30-33`），它直接 `uri = uri.toString()` 透传原始 uri——那种情况极少（类型无法判定的 provider）。

### 4.5 `new File()` / `Blob` 直接 append

**我读到的原文**：
- RN **确实**实现了 `File` 类：`Libraries/Blob/File.js:22` `class File extends Blob`，并在 `Libraries/Core/setUpXHR.js:33` 注册为全局 `File`。
- 但 `Libraries/Blob/Blob.js:57-60` 的构造函数**只支持从其它 Blob/字符串创建**：
  ```js
  /**
   * Constructor for JS consumers.
   * Currently we only support creating Blobs from other Blobs.
   */
  constructor(parts: Array<Blob | string> = [], options?: BlobOptions)
  ```
- 而 multipart 构造（`NetworkingModule.kt:957-1006`）只认三种 part：`string`、`uri`、否则报 `Unrecognized FormData part.`。**没有 `blob` 分支**。

**结论**：
- **不要**试图 `new File(...)` 或把 `Blob` append 进 FormData 来上传本地文件——**`NetworkingModule` 的 multipart 构造器不支持 blob part**。
- **必须**用 `{ uri, name, type }`。
- 这解释了本仓库 `mobile/src/api/itemWrites.ts` 的 `createItem` / `createItemsBulk` 为什么要 `as unknown as Blob` 断言——那是为了绕过 TS 类型（`FormDataValue` 的类型和 DOM 的 `FormData.append` 签名不一致），运行时走的正是 `uri` 分支，（**我的判断**）这个断言是必需且无害的。

### 4.6 上传进度

**我读到的原文**：
- `fetch` 不暴露上传进度。`react-native/Libraries/Network/fetch.js` 只是 `require('whatwg-fetch')` 再导出 `global.fetch`；`whatwg-fetch/dist/fetch.umd.js:540` 只创建 `XMLHttpRequest` 并绑定 `xhr.onload`，**从未触碰 `xhr.upload`**。
- **但 RN 的 XHR 支持**：`XMLHttpRequest.js:320` 有 `__didUploadProgress(requestId, progress, total)`，`XMLHttpRequest.js:576-577` 把它接到 native 的 `didSendNetworkData` 事件；native 侧 `NetworkingModule.kt:790-812` 用 `ProgressRequestBody` 包装请求体并在写入时上报。
- 触发条件是 `XMLHttpRequest.js:572`：`const incrementalEvents = this._incrementalEvents || !!this.onreadystatechange || !!this.onprogress;`——**要挂 `onprogress`（或 `upload.onprogress`）才会启用**。

**结论**：
- 需要上传进度 → **用 `XMLHttpRequest`**，监听 `xhr.upload.onprogress`。
- `fetch` 做不到，不要在这上面浪费时间。
- 对本轮（单张衣物图片）而言，**进度条不是必需的**；用 `fetch` + 禁用重复点击 + 一个"上传中"状态就够。

### 4.7 大图注意事项

**我读到的原文 / 已验证的约束**：
- 后端单文件上限 **20MB**：`image_service.py:204` `if len(image_data) > 20 * 1024 * 1024: return False`。
- 后端像素上限：`image_service.py:88` `limit_pixels = int(settings.max_image_megapixels * 1_000_000)`，默认 50MP（`app/config.py:114`）。
- 内存：RN 的 multipart 把文件**以流**交给 OkHttp（`RequestBodyUtil.create(partContentType, fileInputStream)`，`NetworkingModule.kt:1001`），不是一次性读进 JS 内存——**我的判断**：JS 侧内存压力不大；真正的压力在 native 解码阶段（picker 的 Glide 会把整张图解成 Bitmap）。
- 超时：本仓库 `mobile/src/api/client.ts` 的 `requestMultipart` 用 `UPLOAD_TIMEOUT_MS` 给上传单独设了更长的预算，这是对的——默认 15s JSON 超时对照片太短。

## 5. 可直接复制使用的 TypeScript 示例

以下示例**只使用本报告确认过的 API**。对应本仓库现有的 `mobile/src/media/photoPicker.ts`，可作对照。

```ts
import * as ImagePicker from 'expo-image-picker';
import { ImageManipulator, SaveFormat } from 'expo-image-manipulator';

/** 上传用的最小形状，正好匹配 RN FormData 的 { uri, name, type }。 */
export type UploadablePhoto = { uri: string; name: string; type: string };

const MAX_EDGE_PX = 1600;
const JPEG_QUALITY = 0.8; // 0..1

/**
 * 相册选图 → 压缩到长边 ≤1600、JPEG 质量 0.8 → { uri, name, type }。
 * 返回 null 表示用户取消；抛出的错误由调用方转成用户可读文案。
 */
export async function pickOnePhotoFromLibrary(): Promise<UploadablePhoto | null> {
  // Android 13+ 上这个调用申请的是空权限列表（ImagePickerModule.kt:258-266），
  // 所以不能把 granted===false 当作阻止选图；只处理「永久拒绝」。
  const permission = await ImagePicker.requestMediaLibraryPermissionsAsync();
  if (!permission.granted && permission.canAskAgain === false) {
    throw new Error('PERMISSION_DENIED_PERMANENTLY');
  }

  const result = await ImagePicker.launchImageLibraryAsync({
    mediaTypes: ['images'],     // SDK 57 推荐：MediaType 字符串数组（MediaTypeOptions 已 @deprecated）
    allowsMultipleSelection: false,
    allowsEditing: false,
    quality: 1,                 // 见下方说明
    exif: false,
  });

  // 取消时 assets 是 null（ImagePicker.types.d.ts:351-360），不要用 assets.length 判断。
  if (result.canceled) return null;
  const asset = result.assets[0];
  if (!asset) return null;

  return normalizeForUpload(asset);
}

/** 相机拍照，流程同上。CAMERA 由模块自行声明，无需手写 manifest。 */
export async function captureOnePhoto(): Promise<UploadablePhoto | null> {
  const permission = await ImagePicker.requestCameraPermissionsAsync();
  if (!permission.granted) throw new Error('CAMERA_PERMISSION_DENIED');

  const result = await ImagePicker.launchCameraAsync({
    mediaTypes: ['images'],
    allowsEditing: false,
    quality: 1,
    exif: false,
  });
  if (result.canceled) return null;
  const asset = result.assets[0];
  if (!asset) return null;

  return normalizeForUpload(asset);
}

/**
 * 统一重编码：像素转正由 Glide 完成，EXIF 由 Bitmap.compress 天然丢弃，
 * 输出因此自洽，与 picker 选用了哪个 exporter 无关。
 */
async function normalizeForUpload(asset: ImagePicker.ImagePickerAsset): Promise<UploadablePhoto> {
  const context = ImageManipulator.manipulate(asset.uri);

  // width/height 可能是 0（ImagePicker.types.d.ts:250），只有拿到真实值才 resize。
  const { width, height } = asset;
  if (width > 0 && height > 0 && Math.max(width, height) > MAX_EDGE_PX) {
    // 只给一个维度 → manipulator 自动按比例算另一个（ImageManipulatorContext.d.ts:10-13）。
    if (width >= height) context.resize({ width: MAX_EDGE_PX });
    else context.resize({ height: MAX_EDGE_PX });
  }

  const image = await context.renderAsync();
  const saved = await image.saveAsync({
    compress: JPEG_QUALITY,
    format: SaveFormat.JPEG,
  });

  return {
    uri: saved.uri,                                   // file://... in cache dir
    name: `wardrobe-${Date.now()}.jpg`,               // 服务端按扩展名校验
    type: 'image/jpeg',
  };
}

/** append 进 FormData —— type 不可省，否则 native 直接报错。 */
export function toFormData(photo: UploadablePhoto, fields: Record<string, string> = {}): FormData {
  const form = new FormData();
  // RN 的 FormData 只认这种对象形状；TS 类型与 DOM 不一致，故断言。
  form.append('image', { uri: photo.uri, name: photo.name, type: photo.type } as unknown as Blob);
  for (const [k, v] of Object.entries(fields)) form.append(k, v);
  return form;
}

/** 上传：不要设置 Content-Type，boundary 由 OkHttp 生成。 */
export async function uploadPhoto(photo: UploadablePhoto, token: string): Promise<Response> {
  return fetch(`${API_BASE}/api/v1/items`, {
    method: 'POST',
    headers: {
      Accept: 'application/json',
      Authorization: `Bearer ${token}`,
      // 故意不写 Content-Type。
    },
    body: toFormData(photo, { skip_ai: 'false' }),
  });
}
```

**关于示例里 `quality: 1` 的选择（我的说明）**：`quality: 1` 会走 `RawImageExporter` 字节复制，保留原图与 EXIF——**这没关系**，因为紧接着的 manipulator 会重编码。选 `1` 是为了避免"被 picker 压一次、再被 manipulator 压一次"的二次有损。若改成 `0.6`，结果同样正确（§3.2 路径 C），只是多一次有损。

## 10. 五个最关键的结论

1. **picker 返回的 uri 一定是 `file://`**（`MediaHandler.kt:69`），不需要 `content://` 转换；RN 两种 scheme 都支持（`RequestBodyUtil.kt:75`）。
2. **`TAG_ORIENTATION` 会被 picker 的 `copyExifData` 排除**（`ImagePickerUtils.kt:217`）——所以"sdk 57 的 picker 会导致二次旋转"这个说法**不成立**；四条客户端路径实测 pHash 全部相同且方向正确。
3. **仍然要过 `expo-image-manipulator`**，但理由是：让方向处理不依赖 `quality` 取值（现正确性依赖三个 exporter 隐式互补）、满足后端 20MB/50MP 硬限制、且 manipulator 输出 EXIF 干净（该模块全目录零 `ExifInterface` 引用）。
4. **（仅原生网络栈）FormData 必须用 `{ uri, name, type }` 且 `type` 不可省**——省了 native 直接报 `Binary FormData part needs a content-type header`（`NetworkingModule.kt:972`）；`Blob`/`new File()` 在 multipart **不支持**（构造器只认 `string`/`uri`）。
5. **单件 `POST /items` 没有幂等键**，只有 `/items/bulk` 的 `upload_keys` 有；单件重试靠 pHash 返回 **409 硬失败**，不是幂等成功。

## 11. 与常见写法不一致的坑

1. **`copyExifData` 排除 Orientation**——最常见的博客/经验说法（含本仓库注释）说它抄回旧标签，实际被过滤。
2. **`quality: 1` 是"原始字节复制"而非"最高质量压缩"**（`MediaHandler.kt:50` + `ImagePickerConstants.kt:7`）——传 `quality: 1` 时 `resize`/`compression` 类选项根本不生效。
3. **`requestMediaLibraryPermissionsAsync()` 在 Android 13+ 申请空权限列表**（`ImagePickerModule.kt:258-266`）——不要用它判断"能否选图"。
4. **`assets` 在取消时是 `null` 而非 `[]`**（`ImagePicker.types.d.ts:351-360`）——判别联合，TS 会强制你先查 `canceled`。
5. **`width`/`height` 可能是 `0`**（`ImagePicker.types.d.ts:250`）——直接拿去做 resize 的除法会炸。
6. **手写 `Content-Type` 会被 OkHttp 覆盖**（`BridgeInterceptor.kt:43-46`）——不写才是对的。
7. **`fetch` 没有上传进度**，但 RN 的 XHR 有（`XMLHttpRequest.js:576-577`）——需要进度条必须换 XHR。
8. **`MediaTypeOptions` 已 `@deprecated`**（`ImagePicker.types.d.ts:19`），传它会在运行时 `console.warn`（`src/utils.ts:19-21`）；用 `['images']`。
9. **`manipulateAsync` 已 `@deprecated`**（`ImageManipulator.d.ts:15`）——用 `ImageManipulator.manipulate()`。
10. **`mediatypes` 单字符串需转数组**：`parseMediaTypes` 里 `if (typeof mediaTypes === 'string') return [mediaTypes]`（`src/utils.ts:25-27`），注释明确说 "Unlike iOS, Android can't auto-cast to array"。
11. **不要用 `android/build/generated/autolinking/autolinking.json` 判断 Expo 模块是否入包**——本项目实测该文件只列 9 个 RN 依赖、不含 `expo-image-picker`/`expo-image-manipulator`，但 2026-09-27 构建的 APK 里两者**确实存在**（`classes3.dex` 中分别 181 / 93 次引用）。它是 RN 自动链接的旧快照，与 Expo Modules 的链接机制不是同一套。要确认是否入包，**扫 dex**：`unzip -o -q app-release.apk '*.dex' && python3 -c "print(open('classes3.dex','rb').read().count(b'expo/modules/imagepicker'))"`。

## 12. 与 Expo `fetch` 的关系（必读，否则会得出相反结论）

**这份报告里关于 FormData 分片的部分只描述 React Native 的原生网络栈，而本仓库并不使用它。**
两处结论看似矛盾，实际是两个不同的执行路径；这里把边界讲清楚。

### 12.1 决定走哪条路的是一个环境变量

`mobile/node_modules/expo/src/winter/runtime.native.ts:41-53`：

```ts
const useRnFetch =
  process.env.EXPO_PUBLIC_USE_RN_FETCH === '1' || process.env.EXPO_PUBLIC_USE_RN_FETCH === 'true';

if (!useRnFetch) {
  ...
  install('fetch', () => require('./fetch').fetch);   // 替换全局 fetch
}
```

本仓库的 `.env` / `.env.example` / `app.json` **都没有**设置 `EXPO_PUBLIC_USE_RN_FETCH`，
因此 **Expo 的 `fetch` 生效**，全局 `fetch` 被替换。

### 12.2 两条路径对同一个 FormData 的处理完全不同

| | RN 原生网络栈（`USE_RN_FETCH=1`） | **Expo `fetch`（本仓库实际路径）** |
| --- | --- | --- |
| 谁读分片 | `NetworkingModule.kt`（Kotlin，`FormData.getParts()`） | `convertFormData.ts`（JS，`formData.entries()`） |
| `{uri}` 分片 | ✅ 支持（用 FileInputStream 读文件） | ❌ `throw new Error('Unsupported FormDataPart implementation')` |
| `{uri}` 缺 `type` | ❌ 报 `Binary FormData part needs a content-type header` | 无关（根本到不了那一步） |
| `Blob` / `File` 分片 | ❌ 构造器只认 `string` 与 `uri` 两个键 | ✅ **唯一被支持的形态**（`Blob` 或带 `bytes()` 的对象） |
| body 怎么发 | OkHttp `MultipartBody`（boundary 由 OkHttp 生成） | JS 里拼好 `Uint8Array` + boundary，作为普通 body 发出 |
| 手写 `Content-Type` | 会被 OkHttp 带 boundary 的值覆盖 | **绝对不能写**，否则覆盖掉 JS 生成的 boundary |

两张表都是真的；**它们描述的是不同的代码**。

### 12.3 所以本仓库必须用 `Blob`

`convertFormData.ts` 只接受三种分片（`string` / `Blob` / 带 `bytes()` 的对象），
其余一律抛错，且该错误发生在 `fetch` 内部 —— **请求根本不会发出**，
所以服务端零日志、客户端也无超时，表现为「按钮一直转然后提示上传失败」。

这就是为什么 `mobile/src/api/itemWrites.ts` 的 `appendFilePart()` 用的是：

```ts
const file = new FsFile(photo.uri);                       // expo-file-system，implements Blob
form.append(field, file as unknown as Blob, photo.name);  // name 会成为 multipart filename
```

**实测证据**：改用它之后 `POST /api/v1/items` 立刻返回 **201 Created**（改之前后端完全没有该请求）。
回归测试：`node scripts/verify/formdata-part-contract.mjs`（13 项，直接读 Expo 的序列化器源码断言）。

### 12.4 什么情况下这份报告的原生结论才适用

只有当你在 `.env` 里显式设置 `EXPO_PUBLIC_USE_RN_FETCH=1` 时，全局 `fetch` 才回落成 RN 原生实现，
此时：
- `{uri,name,type}` 才是正确写法，且 `type` 必填；
- `Blob`/`File` 分片**反而会失败**；
- `scripts/verify/formdata-part-contract.mjs` 会失败 —— 那是**预期**的，说明契约变了。

换言之：**这两套写法是互斥的，不能混用**；判断依据是 `EXPO_PUBLIC_USE_RN_FETCH` 那一行。
